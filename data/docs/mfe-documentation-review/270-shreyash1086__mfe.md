## Observações

**1. README.md:4.** O README diz que o projeto tem três módulos e repete o número na árvore de pastas, que mostra só shell-app, module-cloud-labs, module-dashboard e module-virtual-machine (README.md:11-16), no diagrama de carga, que liga o shell a três `remoteEntry.js` (README.md:24-26), em "Build and start all 4 containers" (README.md:39), em "Shell waits for all 3 modules" (README.md:46) e em "4 copies total" (README.md:113). O snapshot tem onze aplicações frontend na revisão estrutural: o shell, nove módulos `module-*` e o `shared-design-system`; o shell carrega os nove por rota (revisão de composição, relações 1 a 9). Que é um conjunto de micro-frontends se confirma; o número, não. "production-ready" é avaliação do autor, sem artefato que a decida.

**2. README.md:4.** Cada aplicação tem um Dockerfile e um serviço próprios no docker-compose.yml, e a revisão de build e deploy registrou deploy `separado` para as onze. A frase fala dos três módulos, mas a propriedade vale para todos, e para o shell e o design system também.

**3. README.md:4.** O shell-app é o host: monta o layout, a autenticação e o tema, e carrega os módulos por rota (shell-app/src/App.jsx:167-277, 290-297). "orchestrated" aqui é papel de host, não orquestração de contêineres, que a afirmação 5 atribui ao compose.

**4. README.md:12.** O shell carrega os nove módulos em runtime: cada um é um `React.lazy` sobre `loadRemoteComponent`, que injeta o `remoteEntry.js` só quando a rota é aberta (shell-app/src/App.jsx:15-77; shell-app/src/remotes/remoteLoader.js:51-65). "all modules" vale para os nove do snapshot. A mesma afirmação aparece em README.md:30 ("The Shell **loads** those components at runtime — not at build time"), no título "Shell CONSUMES them" (README.md:88) em docs/ARCHITECTURE.md:3 ("the `shell-app` composes remotes at runtime") e no diagrama "How Modules Connect" (README.md:19-27), em que o navegador abre o shell em `http://localhost:3000` e o shell busca o `remoteEntry.js` de cada módulo em `http://localhost:3001`–`3003` (README.md:22-26). O diagrama confere com o ramo fora do Docker do `index.html` do shell, que aponta cloud-labs, dashboard e virtual-machine para essas três portas (shell-app/public/index.html:38-40), mas esse ramo tem dez URLs, `localhost:3001`–`3010`, para os nove módulos e o design system (shell-app/public/index.html:36-47); as três do diagrama voltam ao número da afirmação 1. No Docker, as URLs são caminhos relativos do gateway (afirmação 31). A porta 3000 é a do `devServer` (shell-app/webpack.config.js:65), detalhe de execução.

**5. README.md:16.** O docker-compose.yml sobe o gateway, o design system, os nove módulos e o shell numa rede comum (docker-compose.yml:3-184). É o único arquivo que junta as unidades para execução; não há workspace nem CI (revisão estrutural, Notas; revisão de build e deploy, Leitura).

**6. README.md:29.** Cada módulo gera um `remoteEntry.js` e expõe o próprio `App`, um componente React (ex.: `./CloudLabsApp` em module-cloud-labs/webpack.config.js:46-48; as nove exposições estão nas relações 1 a 9 da revisão de composição). O título "Each module EXPOSES itself" (README.md:74) e os comentários dos webpack dos módulos ("Entry file exposed to shell", module-cloud-labs/webpack.config.js:31; "What we expose to the outside world", :47) repetem a afirmação. O design system também gera `remoteEntry.js`, mas expõe tokens, CSS, contexto e vários componentes (shared-design-system/webpack.config.js:36-49), não um só.

**7. README.md:46.** O compose não declara `healthcheck` em nenhum serviço, e o `depends_on` do shell é uma lista simples (docker-compose.yml:168-178), que só ordena a partida, como registrou a revisão de build e deploy. O bloco de README.md:152-158, com `condition: service_healthy` e serviços `auth`, `dashboard` e `profile`, não corresponde ao docker-compose.yml do snapshot. A afirmação é `contradita`: o shell não espera healthcheck, e são nove módulos, não três.

**8. README.md:103.** O título e o bloco que o segue (README.md:105-109) mostram o shell importando os remotes por nome, `lazy(() => import("auth/AuthApp"))`, com os remotes declarados no webpack do shell (README.md:92-100). No snapshot, o shell não declara remotes para os módulos (comentário em shell-app/webpack.config.js:32-33; só `sharedDesignSystem` em :34-47) e não usa `import()` de módulo remoto: cada `React.lazy` recebe a função de `loadRemoteComponent`, que injeta o script e pede o módulo ao container com `container.get` (shell-app/src/App.jsx:15-21; shell-app/src/remotes/remoteLoader.js:51-65). O que se confirma é o uso de `React.lazy` e `Suspense`; o modo de importar, não. O comentário "Loaded at RUNTIME, not build time" do bloco (README.md:106) cabe na afirmação 4.

**9. README.md:113-114.** `react` é compartilhado como `singleton` em todas as onze configurações de webpack (ex.: module-cloud-labs/webpack.config.js:50-53; shell-app/webpack.config.js:52; shared-design-system/webpack.config.js:51-54), e o shell inicializa o escopo compartilhado antes de cada container (shell-app/src/remotes/remoteLoader.js:40, 45). Os comentários das entradas repetem a ideia: "so that shared modules (React) can be negotiated between host and remotes" (module-cloud-console/src/index.js:2-3, igual em outros cinco módulos) e "Async boundary required for Module Federation shared module negotiation" (shell-app/src/index.js:1). O "4 copies total" (README.md:113) volta ao número da afirmação 1.

**10. README.md:120.** As onze aplicações têm Dockerfile de dois estágios: build em `node:18-alpine` e serviço em `nginx:alpine` (ex.: module-cloud-labs/Dockerfile:1-22). O bloco de README.md:122-136 é mais simples que os Dockerfiles do snapshot, que usam a raiz como contexto e copiam o `shared-design-system` antes de instalar (module-cloud-labs/Dockerfile:6-7, 10). docs/ARCHITECTURE.md:11 repete o multi-estágio ("multi-stage builds retained") e acrescenta o `npm ci` quando há lockfile (module-cloud-labs/Dockerfile:11), detalhe de instalação.

**11. README.md:164, 167.** O README diz que um módulo pode ser escalado sozinho, com o exemplo do dashboard em três instâncias atrás de um balanceador. No snapshot, todos os serviços do compose têm `container_name` fixo (ex.: `mfe-dashboard`, docker-compose.yml:54-58), e o Docker Compose não cria mais de um contêiner para um serviço com nome fixo; o gateway encaminha para esse nome único (nginx/nginx.conf:49-50). Não há balanceador no snapshot. A afirmação é `contradita` pelos artefatos de deploy; a seção se chama "Scaling in Production", e nada no snapshot mostra uso em produção.

**12. README.md:171.** Cada módulo é um serviço próprio do compose, com imagem própria, e a revisão de build e deploy registrou deploy `separado` para os nove. A mesma afirmação aparece em README.md:197 ("Deploy independently without redeploying others") e em docs/ARCHITECTURE.md:3 ("keep each micro-frontend independently deployable"). O comando do bloco usa um serviço `auth` (README.md:175), que não existe no docker-compose.yml. Há um limite, registrado na revisão de build e deploy: o CSS do shell é gerado a partir das fontes dos módulos (shell-app/Dockerfile:13-22), e uma classe nova num módulo só ganha estilo quando o shell é reconstruído.

**13. README.md:171.** Nada no snapshot descreve como um contêiner é trocado sem interrupção: não há réplicas, estratégia de atualização nem balanceador (docker-compose.yml:145-156, por exemplo). Fica `sem corroboração`.

**14. README.md:194.** Que cada módulo possa ser desenvolvido por um time próprio é organização de trabalho; o snapshot não tem artefato que confirme ou desminta (não há CODEOWNERS nem divisão de responsabilidade).

**15. README.md:195.** Cada módulo tem `index.html`, `devServer` e bootstrap próprios e renderiza o `App` sozinho (revisão estrutural; module-cloud-labs/webpack.config.js:69-75; module-cloud-labs/src/bootstrap.js:3-7). O `App` cria o próprio `BrowserRouter` quando não está dentro do roteador do shell (module-cloud-labs/src/App.jsx:18-33), como diz o comentário "Standalone module-auth needs its own router for useNavigate, but the shell already provides one when the remote is mounted there" (module-cloud-labs/src/App.jsx:23-24; em module-cloud-console/src/App.jsx:23-24, "module-profile"). Sem a ponte do shell, o `AuthContext` do módulo usa a própria verificação de autenticação ("Standalone mode: use existing auth check", module-assessment/src/AuthContext.jsx:128). Os módulos ainda dependem do `remoteEntry.js` do design system, na porta 3010 quando rodam sozinhos (module-cloud-labs/webpack.config.js:36-37).

**16. README.md:196.** Não há nenhum workflow de CI no snapshot (revisão de build e deploy, Leitura), e o próprio docs/ARCHITECTURE.md:57 lista os workflows como próximo passo. A frase diz o que cada módulo "can" ter; sem pipeline no snapshot, fica `sem corroboração`.

**17. README.md:198.** As bibliotecas que as unidades de fato compartilham pela federação (`react`, `react-dom`, `react-router`, `react-router-dom` e `shared-design-system`) estão como `singleton` em todos os módulos e no shell (module-cloud-labs/webpack.config.js:49-67; shell-app/webpack.config.js:51-58). Com `singleton`, só uma versão é carregada em runtime, a mesma para todas as unidades, o que é o oposto de cada módulo usar uma versão diferente. As versões declaradas também são iguais: `react` `^18.2.0` e `react-router-dom` `^7.15.1` em todos os módulos e no shell (ex.: module-cloud-labs/package.json:11-14; shell-app/package.json:12-15).
