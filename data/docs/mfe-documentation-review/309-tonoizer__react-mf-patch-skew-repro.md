# 309 — tonoizer/react-mf-patch-skew-repro

## Repository overview

The only documentation is English README.md, the sole `documentation` artifact in `artifacts.csv`. It presents the repository as a minimal reproduction of an `@module-federation/vite` 1.21.6 defect (README.md:1-3). Four federated Vite apps share the React family as singleton, but each pins a React 19.2.x patch, and production build crashes. README includes:
- per-app role table (README.md:9-14);
- common `shared` configuration (README.md:16-24);
- commands rebuilding/serving all four apps and running the Playwright script (README.md:33-45);
- expected results (README.md:48-52), versioned evidence list (README.md:56-61) and two notes (README.md:65-66).

Described architecture matches previous reviews:
- four React/Vite units in a pnpm workspace (3.4.3);
- top-level host with two remotes, and remote_a as nested host of remote_c (3.4.5 #1-#3);
- separate builds with local execution only (3.4.6).

The sole discrepancy is claim 2: README says each app installs a different patch, but host and remote_c pin the same version. Claimed runtime consequences (natural-loading crash, forced error #527) have only versioned `evidence/` outputs as artifacts, recorded by local execution (README.md:54). The composition review already used them as context (3.4.5, Repository overview).

`doc-*` occurrences: both (README.md:11 and :12, `doc-host-remote`) are claims 3 and 4.

## Observations

**1. README.md:3.** The sentence describes the arrangement and resulting failure. Configuration confirms the arrangement:
- all four apps use the federation plugin in build (3.4.2);
- all declare the React family singleton with `requiredVersion: '^19.2.4'` (host/vite.config.js:5-11, and the same block at lines 5-11 of the other three `vite.config.js` files).

Failure has no artifact beyond versioned outputs from one execution. Natural loading leaves host blank with `Cannot read properties of null (reading 'useState')`. Forcing `loadShare` of `react-dom/client` from remote_a and remote_b under host scope produces error #527 with 19.2.8 versus 19.2.4 and 19.2.6 (evidence/RESULT.json:5-15; evidence/force-527.json; evidence/force-527-remote_b.json). The identified cause appears in recorded remote_a build: `loadShare` of `react-dom/client` statically imports the `loadShare` of shared `react` (evidence/eager-static-import-proof.txt:10-13). The evidence filename already describes this as "static import of shared react + inlined local react-dom".

However, in natural loading the recorded stack shows host App rendered by remote_c `react-dom/client` (evidence/RESULT.json:12), and remote_c has host’s same patch. Thus natural crash does not arise from a patch difference between these two. This remains context without changing general mechanism corroboration.

Repetitions:
- expected results (README.md:50-52);
- evidence summary (evidence/RESULT.json:3), not a document.

**2. README.md:3.** All four apps pin their own `react`/`react-dom` pair (host/package.json:11-12; remote_a/package.json:11-12; remote_b/package.json:11-12; remote_c/package.json:11-12). This part is confirmed. However, "Different" does not apply to all: host and remote_c pin 19.2.8. Lockfile resolves only three `react` versions: 19.2.4, 19.2.6 and 19.2.8 (pnpm-lock.yaml:780-788). README’s own table shows both apps at 19.2.8 (README.md:11, 14), as does evidence/RESULT.json:52-55. Under step 3, the disproven part makes the claim `contradicted`. The relevant experimental patch difference is remote_a and remote_b versus host (claim 1).

Repetition: README.md:65, "Each app pins its own `react` / `react-dom` patch in `package.json` so pnpm installs distinct versions per package". Same qualification applies: two packages receive the same version.

Version 19.2.8 matches host/package.json:11-12. Host exposes no modules, as the table implies by listing only "remotes".
