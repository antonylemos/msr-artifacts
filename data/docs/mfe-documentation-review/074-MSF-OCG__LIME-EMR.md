# 074 — MSF-OCG/LIME-EMR

## Repository overview

Documentation is entirely in English. Its center is root `README.md` (1335 lines). It presents LIME EMR as an OpenMRS 3 distribution built on Ozone HIS, with three configuration levels (distro, country, site) and deployments in Mosul, Matsapha and Bunia (README.md:3-5, :85-91, :127-133). On frontend, it says the interface follows "OpenMRS 3 ESM microfrontend architecture", distro defines modules and versions in `spa-assemble-config.json`, each site adds its own UI configuration through `SPA_CONFIG_URLS`, extensions such as `patient-flags-list` occupy patient chart slots, and an app can be removed from a site through configuration (`remove`, `Display conditions`), the build import map or `frontendModuleExcludes` (README.md:189, :262, :332, :838, :1027-1102). Previous reviews show the same picture: no frontend application in snapshot (3.4.3), no code composition construct (3.4.4) and no relationship between snapshot units (3.4.5). All 42 modules are external, as is the composing app-shell; versioned content consists of their configuration and build-time map maintenance (3.4.5 Overview; 3.4.6 Overview). ## Observations

**1. README.md:101.** The capability list says the system runs in Docker Compose-orchestrated containers with Traefik for SSL. The same idea returns at README.md:158 ("a set of Docker containers orchestrated by Docker Compose") and README.md:936-944 ("a single Docker Compose stack behind a Traefik reverse proxy"). Snapshot confirms part: a Traefik compose (scripts/docker-compose-traefik.yml:6-11), an override adding a variable to service `frontend` (scripts/docker-compose-openmrs-override.yml:16-18), and a frontend image in profile `bundled-docker` (distro/pom.xml:901-909). Compose defining service `frontend` comes from Ozone and is absent from snapshot (3.4.6 Overview). "single-command VPS provisioning" uses a tool in another repository (README.md:911-932). Hence the claim is `partial`.

**2. README.md:129.** Distro defines frontend modules: the versioned list is in `distro/configs/openmrs/frontend_assembly/spa-assemble-config.json:3-46`. All three sites receive distro ZIP as a dependency and unpack it (sites/mosul/pom.xml:22-29, :36-48; sites/matsapha/pom.xml:24; sites/bunia/pom.xml:25), hence share the same base. Each site removes some base modules (row 23), as README itself allows by saying each level "can selectively override or extend" (README.md:133). The same claim appears at docs/README.md:25 and, as "OpenMRS configuration covers the backend modules, frontend microfrontends" (`doc-mfe-term` occurrence), at README.md:581.

**3. README.md:149-150.** The diagram says Maven build generates ZIPs and Docker images and GitHub Actions deploys to server. The first part is confirmed: distro is ZIP-packaged (distro/assembly.xml:10-19), and images are built and pushed in profile `bundled-docker` (distro/pom.xml:958-971). Artifacts refute the second. `deploy.yml` runs only when called by another workflow (.github/workflows/deploy.yml:3-4), and its only call, in `deploy-to-dev` job of `ci.yml`, is commented out along with subsequent e2e tests (.github/workflows/ci.yml:25-48). Job `release` only publishes, without deployment (.github/workflows/ci.yml:50-60). Chain "ci.yml → maven-publish.yml → deploy.yml (deploy to dev) → run-e2e-tests.yml" (README.md:536-549) repeats the claim in more detail, as do README.md:950-951 ("automated deployment to the dev environment", "deploy to UAT") and docs/README.md:183-184. Names "Build all configurations and deploy" of `build-all.yml` and `build-all-vm.yml` and README table (:551-552) also repeat it, but both workflows only run `mvnw clean package` (.github/workflows/build-all.yml:50-51; .github/workflows/build-all-vm.yml:36-37). Under the rule, the claim is `contradicted`. ZIP and image generation is confirmed.

The claim is `partial`. Repetitions: diagram at README.md:491 ("Traefik terminates SSL and proxies requests to the OpenMRS frontend") and docs/README.md:46-53.
