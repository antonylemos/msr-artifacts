# 074 — MSF-OCG/LIME-EMR

## Leitura do repositório

A documentação é toda em inglês. O centro é o `README.md` da raiz (1335 linhas). Ele apresenta a LIME EMR como uma distribuição OpenMRS 3 montada sobre a Ozone HIS, com três níveis de configuração (distro, país, site) e implantações em Mosul, Matsapha e Bunia (README.md:3-5, :85-91, :127-133). Sobre o frontend, ele diz que a interface segue a "OpenMRS 3 ESM microfrontend architecture", que a distro define os módulos e suas versões em `spa-assemble-config.json`, que cada site acrescenta a própria configuração de UI por `SPA_CONFIG_URLS`, que extensões como `patient-flags-list` ocupam slots do patient chart e que um app pode ser tirado de um site por configuração (`remove`, `Display conditions`), pelo import map no build ou pela lista `frontendModuleExcludes` (README.md:189, :262, :332, :838, :1027-1102). As revisões anteriores mostram o mesmo quadro: nenhuma aplicação frontend no snapshot (3.4.3), nenhuma construção de composição no código (3.4.4) e nenhuma relação entre unidades do snapshot (3.4.5). Os 42 módulos são externos, o app-shell que os compõe também, e o que está versionado é a configuração deles e a manutenção dos mapas no build (3.4.5 Leitura; 3.4.6 Leitura). O README confere com a configuração no mecanismo, mas não nos números: fala em "41 modules" mais dois módulos Madiro e em "Core UI 8.0.1", quando a configuração tem 42 módulos e `coreVersion` `10.0.1-pre.5320` (distro/configs/openmrs/frontend_assembly/spa-assemble-config.json:2-46; linhas 5 e 13). Também descreve uma cadeia de CI que faz deploy automático para dev e UAT, mas a única chamada ao workflow de deploy está comentada (linha 3). Duas funcionalidades que ele diz herdadas por todos os sites são tiradas da UI de algum site: o follow-up table e o app de tarefas (linhas 16 e 19).

O README também traz bastante coisa que não é afirmação sobre as unidades frontend. O nível de país aparece em vários trechos (README.md:130, :246-250, :274-276, :308), mas `countries/` não existe no snapshot e o `pom.xml` da raiz só agrega `distro` e os três sites (pom.xml:12-15). O próprio roadmap propõe remover esse nível (README.md:1333), e `setting_up_new_site.md:36-40` diz que Matsapha herda direto da distro. A herança por download, desempacotamento, exclusão e cópia de ZIPs Maven (README.md:133, :303-321; docs/README.md:29) é o empacotamento da distribuição como um todo, e os `pom.xml` dos sites a confirmam (sites/mosul/pom.xml:22-29, :36-48). As seções de formulários clínicos, address hierarchy, OpenFn, credenciais, backup e restauração, conceitos e as tabelas de flags e tarefas (README.md:615-790, :800-821, :886-895, :997-1016, :1104-1233, :1285-1302) tratam de metadados, backend e operação. Patient flags e RDE são ligados por feature flags do `@openmrs/esm-app-shell` (README.md:833, :848-852, :1236-1259), que é detalhe interno do app-shell. A distro liga `patient-flags` e `rde` (distro/configs/openmrs/frontend_config/msf-frontend-config.json:18-20), e os sites só ligam `rde` (sites/mosul/configs/openmrs/frontend_config/msf-mosul-frontend-config.json:9-10), como o README diz. A Seção 6 descreve ferramentas de outro repositório, privado, e um processo manual: `deploy-lime.sh`, o deploy manual nas VMs FiWi e a hospedagem (README.md:911-932, :954, :956-962, :976-980; docs/README.md:185). Nada disso está no snapshot, e ficou fora da tabela como sistema externo. A lista de imagens anuncia "8 total" e lista 7 (README.md:511-521). O `distro/pom.xml` declara 7 imagens (distro/pom.xml:892-954). Isso não muda o que se diz da imagem de frontend (linha 12). O roadmap (README.md:1327-1335) traz intenções, não a descrição do snapshot. Entre elas estão "merge logic for frontend config JSONs" (:1329) e um artefato único por site (:1331).

## Observações

**1. README.md:101.** A lista de capacidades diz que o sistema roda em contêineres orquestrados por Docker Compose, com Traefik para SSL. A mesma ideia volta em README.md:158 ("a set of Docker containers orchestrated by Docker Compose") e em README.md:936-944 ("a single Docker Compose stack behind a Traefik reverse proxy"). O snapshot confirma parte disso. Há um compose do Traefik (scripts/docker-compose-traefik.yml:6-11), um override que acrescenta uma variável a um serviço `frontend` (scripts/docker-compose-openmrs-override.yml:16-18) e uma imagem de frontend no perfil `bundled-docker` (distro/pom.xml:901-909). O compose que define o serviço `frontend` vem da Ozone e não está no snapshot (3.4.6 Leitura). O "single-command VPS provisioning" é feito por ferramenta de outro repositório (README.md:911-932). Por isso a afirmação é `parcial`.

**2. README.md:129.** A distro define os módulos frontend: a lista com versões está em `distro/configs/openmrs/frontend_assembly/spa-assemble-config.json:3-46`. Os três sites recebem o ZIP da distro como dependência e o desempacotam (sites/mosul/pom.xml:22-29, :36-48; sites/matsapha/pom.xml:24; sites/bunia/pom.xml:25), então a base é a mesma para todos. Cada site tira alguns módulos dessa base (linha 23), o que o próprio README prevê ao dizer que cada nível "can selectively override or extend" (README.md:133). A mesma afirmação aparece em docs/README.md:25 e, como "OpenMRS configuration covers the backend modules, frontend microfrontends" (ocorrência `doc-mfe-term`), em README.md:581.

**3. README.md:149-150.** O diagrama diz que o build Maven gera ZIPs e imagens Docker e que o GitHub Actions faz o deploy no servidor. A primeira parte se confirma: a distro é empacotada em ZIP (distro/assembly.xml:10-19), e as imagens são construídas e enviadas no perfil `bundled-docker` (distro/pom.xml:958-971). A segunda é desmentida pelos artefatos. `deploy.yml` só roda quando outro workflow o chama (.github/workflows/deploy.yml:3-4), e a única chamada, no job `deploy-to-dev` do `ci.yml`, está comentada junto com os testes e2e que viriam depois (.github/workflows/ci.yml:25-48). O job `release` só publica, sem deploy (.github/workflows/ci.yml:50-60). A cadeia "ci.yml → maven-publish.yml → deploy.yml (deploy to dev) → run-e2e-tests.yml" (README.md:536-549) repete a afirmação com mais detalhe, assim como README.md:950-951 ("automated deployment to the dev environment", "deploy to UAT") e docs/README.md:183-184. Também a repetem os nomes "Build all configurations and deploy" de `build-all.yml` e `build-all-vm.yml` e a tabela do README (:551-552), mas esses dois workflows só rodam `mvnw clean package` (.github/workflows/build-all.yml:50-51; .github/workflows/build-all-vm.yml:36-37). Pela regra, a afirmação é `contradita`. O que se confirma é a geração de ZIPs e imagens.

**4. README.md:160-181.** O diagrama põe o frontend como um único serviço, "OpenMRS Frontend (ESM)", que chama o backend por REST e fica atrás do Traefik, que termina o SSL. Isso combina com a imagem única de frontend (linha 12). No snapshot há o serviço `openmrs` (backend) e o `frontend`, ambos só como override de um compose externo (scripts/docker-compose-openmrs-override.yml:2-3, :16-18), e o Traefik (scripts/docker-compose-traefik.yml:6-26). O Traefik não declara nenhuma rota para o frontend: os únicos labels são os do painel (:20-26), e as regras vêm de um `traefik.yml` montado de fora (:16). A chamada REST também não tem artefato.
