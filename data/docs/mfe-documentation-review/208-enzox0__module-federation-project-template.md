## Leitura do repositório

A documentação está em inglês, em três arquivos: o `README.md` da raiz (701 linhas), único marcado como `documentation` no `artifacts.csv`, e dois guias em `.docs/`, `QUICK_START.md` e `RUNNING.md`. O `artifacts.csv` lista os dois guias com `artifact_types` vazio, mas eles são prosa sobre como o projeto roda, e o próprio README os indica (README.md:674-675). Por isso foram lidos inteiros e entram na tabela como o README. Todas as ocorrências `doc-*` da mineração estão no README.

O que a documentação diz do projeto como um todo confere com as revisões anteriores: um monorepo pnpm/Turbo com um shell host (porta 3000) e quatro microfrontends remotos (3001 a 3004), ligados por Module Federation e carregados em runtime com lazy load, cada um com servidor de desenvolvimento e Dockerfile próprios (3.4.3; 3.4.5 #1-4; 3.4.6 #1-5). As divergências estão em três pontos. O primeiro são os pacotes compartilhados: o README os desenha importados por todas as aplicações (README.md:51-74), mas nenhuma aplicação importa `packages/*` (3.4.4, Notas). O segundo é o build e o deploy. Os pacotes não têm script de build (packages/ui/package.json:7-10). Cada Dockerfile constrói o workspace inteiro (apps/admin-mf/Dockerfile:6-7). O nginx não é proxy reverso (infrastructure/nginx/nginx.conf:13-17). E o deploy é só um `echo` (.github/workflows/cd.yml:14-15). O terceiro é o caminho do `remoteEntry.js`, que um dos guias dá sem o prefixo `/dist` (.docs/RUNNING.md:81). As descrições funcionais das unidades (login e registro, analytics, gestão de usuários e papéis, chat em tempo real e notificações; README.md:28-31, :126-140) são de negócio e não viraram linha. Os remotos do snapshot são stubs: admin, dashboard e messaging só renderizam um título (por exemplo apps/admin-mf/src/exposes.tsx:14), e auth tem um formulário com `alert` (apps/auth-mf/src/exposes.tsx:7-10). O próprio README pede para "Add your business logic to each microfrontend" (README.md:696).

Blocos de código que reproduzem arquivos ou comandos não viraram linha. Vários não batem com o snapshot. Os pacotes aparecem como `@template/...` (README.md:327, :405-414, :466, :487, :514-515), mas o snapshot usa `@mf/...` (apps/shell/package.json:2; packages/ui/package.json:2). O exemplo de `module-federation.config.ts` usa `export default` (README.md:337-348), e os arquivos do snapshot exportam `mfConfig` (apps/shell/module-federation.config.ts:1). Para registrar um remoto novo, o README só manda editar `apps/shell/src/App.tsx` (README.md:351-357) e não cita o `remotes` de `apps/shell/module-federation.config.ts:4-9`. A configuração de produção com URLs `https://*.yourapp.com/remoteEntry.js` (README.md:571-578) não existe no snapshot: o shell embute URLs `localhost` (apps/shell/module-federation.config.ts:5-8; 3.4.6 #5). O `docker-compose build`/`up` com acesso em `http://localhost` (README.md:585-593) também não tem arquivo correspondente: não há docker-compose no snapshot (3.4.6, Leitura).

## Observações

**1. .docs/QUICK_START.md:28-29.** Dá como causa do erro "Failed to fetch dynamically imported module" um microfrontend remoto que não está rodando. A afirmação diz que o shell busca os remotos em runtime nos servidores deles, e as revisões confirmam: o shell importa `authMf/App`, `adminMf/App`, `dashboardMf/App` e `messagingMf/App` com `lazy(() => import(...))` (apps/shell/src/App.tsx:7-10), e cada remote aponta para um `http://localhost:300N/dist/assets/remoteEntry.js` (apps/shell/module-federation.config.ts:5-8). A mesma afirmação se repete em .docs/RUNNING.md:3 ("All remote apps must be running before the shell (host) app can load them"), .docs/RUNNING.md:61-63, README.md:233 e README.md:599-601. Como o carregamento é lazy e por rota (apps/shell/src/App.tsx:36-75), o remote só precisa estar no ar quando sua rota é aberta, não quando o shell sobe. É isso o que "before the shell (host) app can load them" diz.

**2. .docs/QUICK_START.md:46-50.** A tabela de portas lista o shell como host e quatro microfrontends, cada um com a sua porta. São as cinco unidades da revisão estrutural (3.4.3 Resumo), e as portas são as de `server.port` de cada `vite.config.ts` (por exemplo apps/shell/vite.config.ts:15; apps/auth-mf/vite.config.ts:15). A revisão de composição confirma os papéis, com o shell como origem das quatro relações `host → remote` (3.4.5 #1-4). A mesma lista se repete em .docs/RUNNING.md:21-57, no diagrama (README.md:23-32, que também chama os quatro de "Module Federation Remotes"), na árvore de pastas (README.md:117-140) e na tabela de portas do README (README.md:304-310). O shell "Host application (port 3000)" da árvore (README.md:120) também é esta afirmação.

**3. .docs/QUICK_START.md:76.** O shell envolve cada remoto num `ErrorBoundary` dentro da rota (apps/shell/src/App.tsx:39-43, e o mesmo nas rotas de admin, dashboard e messaging), que é o ponto de montagem registrado em 3.4.4. Quando a carga falha, o componente mostra "{moduleName} Unavailable", com uma mensagem própria para erro de rede, e um botão que limpa o estado de erro (apps/shell/src/components/ErrorBoundary.tsx:28-30, :51-69). O "Auto Retry - Click retry when remotes become available" (.docs/QUICK_START.md:78), o parágrafo de .docs/RUNNING.md:70-72, o "error boundaries" de README.md:123 e README.md:688 repetem a afirmação. O botão existe. Os artefatos não mostram se, depois dele, o módulo remoto é buscado de novo.

**4. .docs/QUICK_START.md:77.** O shell monta um `RemoteHealthCheck` (apps/shell/src/App.tsx:78) que lista as quatro URLs de `remoteEntry.js` (apps/shell/src/components/RemoteHealthCheck.tsx:11-16), faz `fetch` em cada uma (:24-38) e repete a verificação a cada 10 s (:56). Repetem a afirmação o indicador "Remote Status" com pontos verdes e vermelhos (README.md:297-299; .docs/QUICK_START.md:38; README.md:605) e "Health Monitoring: Real-time remote status indicators" (README.md:689).
