# 096 — victorlmneves/_nuxt-monorepo-mfe-platform

## Leitura do repositório

A documentação é o README da raiz, em inglês, único arquivo `documentation` do `artifacts.csv`. Ele apresenta o projeto como uma plataforma de micro-frontends num monorepo: um shell Nuxt 3 que orquestra quatro remotes, dois em Vue 2 + Vuetify 2 e dois em Vue 3 + Vuetify 3. Traz uma árvore de pastas comentada (README.md:11-36), uma seção "How it works" sobre isolamento de frameworks, cabeçalho, autenticação por eventos e o contrato `mount`/`unmount` (README.md:40-62), instruções de execução e build, um roteiro para acrescentar um MFE, um exemplo de troca do serviço de autenticação e uma tabela de portas (README.md:138-146). Também diz que o projeto foi construído sobre outro repositório do autor, `nuxt-mf-monorepo` (README.md:5). Essa origem está fora do snapshot e não se liga às unidades, por isso não virou linha.

No geral, o README confere com as revisões anteriores: cinco unidades (3.4.3), quatro relações host → remote por Module Federation e quatro de eventos (3.4.5), build separado por aplicação (3.4.6). As divergências estão no que ele diz que é compartilhado. O cabeçalho seria o único elemento compartilhado (README.md:20, :48), mas só o shell o usa, e o pacote `@mfe/shared` é usado pelas cinco unidades (3.4.2). Além disso, os remotes Vue 3 compartilhariam o Vue 3 com o shell pelo escopo `singleton` (README.md:46), mas o shell não tem `ModuleFederationPlugin` e inicia cada container com um escopo vazio (apps/shell/composables/useMfeLoader.ts:28-32). O próprio comentário do loader diz que cada remote cuida do seu escopo (apps/shell/composables/useMfeLoader.ts:29-30).

Ficaram fora da tabela:

## Observações

**1. README.md:3.** O snapshot tem as cinco unidades da revisão estrutural: o shell Nuxt 3 (`nuxt` em apps/shell/package.json:16) e quatro remotes, dois com `vue` ^2.7.16 e `vuetify` ^2.7.2 (apps/mfe-vue2-checkout/package.json:11-12) e dois com `vue` ^3.5.0 e `vuetify` ^3.7.0 (apps/mfe-vue3-profile/package.json:11-12). "Orchestrated" corresponde às quatro relações host → remote em que o shell escolhe, carrega e monta cada remote (3.4.5 #1-#4). A árvore repete o papel do shell ("Nuxt 3 host", README.md:14), o que está na afirmação 3.

**2. README.md:5.** Os quatro remotes usam o `ModuleFederationPlugin` do webpack (ex.: apps/mfe-vue2-checkout/webpack.config.js:66-73), e o shell consome os containers pelo protocolo do Module Federation, mas sem o plugin (afirmação 30). O workspace pnpm está em pnpm-workspace.yaml:1-3 e o Turborepo em turbo.json:3-18, chamado pelo `build` da raiz (package.json:19). A revisão de dependências marcou `turbo` como `Undetermined` porque a única chamada está em scripts do package.json. Para esta afirmação, que só diz que o projeto usa a ferramenta, basta a configuração.

**3. README.md:13-28.** A árvore nomeia as cinco aplicações com o framework de cada uma, e todas são unidades na revisão estrutural. As versões conferem nos manifestos (ex.: apps/mfe-vue2-admin/package.json:11-12, `vue` ^2.7.16; apps/mfe-vue3-dashboard/package.json:11-12, `vue` ^3.5.0). As portas não entram na afirmação. A mesma lista aparece na tabela "Port map" (README.md:140-146), nos comentários dos comandos de desenvolvimento (README.md:91-94) e no `echo` de scripts/start-local.sh:9-13.

**4. README.md:17.** A página inicial do shell gera um cartão `NuxtLink` para cada descritor do registro, com nome, descrição e o selo Vue 2 ou Vue 3 (apps/shell/pages/index.vue:12-28, :42). Os cartões só levam às rotas `/app/<id>`; a carga acontece na página da afirmação 5.

**5. README.md:18.** A página catch-all acha no registro o descritor cuja rota é prefixo do caminho (apps/shell/pages/app/[...mfe].vue:40-42), monta o remote no `div` de :24 ao abrir (:44-50) e o desmonta ao sair (:52-55). É o ponto de montagem das quatro relações host → remote.

**6. README.md:20.** O `ShellHeader.vue` só é usado pelo shell, nas páginas apps/shell/pages/index.vue:3 e apps/shell/pages/app/[...mfe].vue:3. Nenhum remote o importa: os `App.vue` dos remotes trazem só o próprio título de página (ex.: apps/mfe-vue2-checkout/src/App.vue:1-15). Como exige o passo 3, "compartilhado" só se confirma com ao menos duas unidades usando o elemento, e aqui há uma. A parte "only shared UI element" se confirma: não há outro componente de interface comum, e `packages/shared` só tem tipos, eventos e registro (packages/shared/src/index.ts:1-3). Mas o "shared" é desmentido, então a afirmação é `contradita`. O próprio README explica, em README.md:50, que o cabeçalho fica no shell e aparece acima de cada remote (afirmação 17).

**7. README.md:22.** `useMfeLoader.ts` define `loadRemoteModule`, que resolve o container e o módulo exposto, e `mountMfe`/`unmountMfe`, chamados pela página catch-all (3.4.4, linhas src-load-remote de :13 e :79). "Dynamic" corresponde à carga em execução, depois que se escolhe a rota. O mecanismo, por `<script>`, está na afirmação 28.

**8. README.md:31.** `@mfe/shared` reexporta tipos, autenticação e registro (packages/shared/src/index.ts:1-3; packages/shared/package.json:6-10). As cinco unidades declaram e usam o pacote (3.4.2): o shell pelo registro e pela store (apps/shell/pages/app/[...mfe].vue:30; apps/shell/stores/auth.ts:3), os remotes pelas funções de eventos (ex.: apps/mfe-vue2-checkout/src/bootstrap.js:3). O compartilhamento tem mais de duas unidades e é `corroborada`. A linha seguinte da árvore, "types/ ← UserState, MfeDescriptor, RemoteMount" (README.md:33), detalha o conteúdo, que está em packages/shared/src/types/index.ts:2-33. O pacote não tem build próprio e entra no bundle de cada aplicação pelos aliases (afirmação 35).

**9. README.md:34.** O barramento usa `CustomEvent` em `window` com dois eventos, `mfe:auth-changed` e `mfe:auth-logout` (packages/shared/src/auth/index.ts:3-4, :14, :22), e não depende de framework: o mesmo código serve aos remotes Vue 2 e Vue 3. A revisão de composição registrou uma relação `communication` do shell para cada remote. A mesma afirmação volta no título "Auth state sharing" (README.md:52), em "Auth state crosses framework boundaries via a **framework-agnostic CustomEvent bus** in `packages/shared/src/auth`" (README.md:54) e no comentário de apps/shell/stores/auth.ts:28.

**10. README.md:35.** `MFE_REGISTRY` declara os quatro remotes com rota, URL do `remoteEntry.js`, nome do container e módulo exposto (packages/shared/src/registry.ts:12-61). A página inicial o usa para os cartões (apps/shell/pages/index.vue:42), e a página catch-all para escolher o remote (apps/shell/pages/app/[...mfe].vue:41), que é a linha manual `host-relationship` da revisão de código-fonte. O passo 4 de "Adding a new MFE" ("Add an entry to `packages/shared/src/registry.ts`", README.md:112) repete a afirmação.
