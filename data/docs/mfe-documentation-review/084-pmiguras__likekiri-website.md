# 084 — pmiguras/likekiri-website

## Leitura do repositório

A documentação é toda em espanhol e extensa. O centro é o `README.md` (361 linhas), acompanhado por um `CLAUDE.md` dirigido a agentes, nove ADRs em `docs/adr/`, um guia de integração de módulos (`docs/como-integrar-un-modulo.md`), uma proposta de design system (`docs/design/design-system.md`) e um README por módulo. Os textos descrevem a plataforma como um "microkernel híbrido": um core NestJS que não conhece domínio de negócio, módulos independentes que publicam um manifest assinado e um bundle federado, e duas superfícies, o site público `likekiri.com` (shell React com SSR e ilhas) e o painel `admin.likekiri.com` (SPA cujo menu e páginas vêm dos manifests) (CLAUDE.md:3-5; README.md:3-9). Esse quadro confere com as revisões anteriores: dois shells React/Vite e dez remotes `@module-federation/vite` (3.4.2; 3.4.3), composição só em runtime, sem `remotes` estáticos, com o core como resolvedor das rotas (3.4.4; 3.4.5 Leitura), build próprio para as doze aplicações e deploy separado para os módulos, enquanto os dois shells saem no processo do core (3.4.6). A documentação vai além das revisões no detalhe do fluxo (registry, SSR delegado, widgets) e é, no geral, fiel ao código. As divergências estão em textos que ficaram para trás quando o SSR delegado entrou (linhas 42, 54 e 63), no diagrama do README (linhas 14 e 15), no fluxo da requisição, que esquece os `/assets/*` servidos pelo Caddy (linha 17), na origem dos estáticos de admin do `hello` (linha 44) e no header "estático" do site (linha 62).

O `matches.csv` tem nove ocorrências `doc-*`. Seis estão em linhas da tabela ou nos parágrafos delas: CLAUDE.md:28 (linha 5), README.md:160 e docs/adr/005-admin-por-modulos-y-submenus.md:20 (parágrafo 5), README.md:79 (linha 21), docs/como-integrar-un-modulo.md:17 (parágrafos 5 e 22) e modules/ejemplo-web/README.md:11 (parágrafo 21). As três do ADR 002 são menções sem afirmação: a lista do stack fixada pelo brief, "Module Federation, argon2, zod" (docs/adr/002-stack-y-versiones.md:9), o título da seção "Module Federation: @module-federation/vite 1.20.5" (:29) e o nome da equipe que mantém o plugin, na justificativa da escolha (:32); a escolha do plugin que a seção registra repete a linha 29. Ficaram fora da tabela, por serem detalhe interno do core, segurança, operação ou negócio: a resolução da superfície por `Host` (README.md:66-68), o filtro de rotas e menus por permissão e o manifest de admin vazio sem sessão (README.md:89-90, :103-104; ADR 005, docs/adr/005-admin-por-modulos-y-submenus.md:42-45, :57-59; docs/como-integrar-un-modulo.md:145-147), a manutenção da última versão boa do manifest (README.md:99-100; apps/core/src/registry/registry.service.ts:151-158), as regras de namespace, permissões declaradas e consumidas, manifest estrito e HMAC (README.md:111-121; docs/como-integrar-un-modulo.md:20-37), a UI server-driven por `ShellSetting` além do que está nas linhas 9 e 46 (README.md:123-130; docs/adr/006-server-driven-shell-y-tipo-de-cuenta.md:16-56), a seção de segurança (README.md:273-290), o cache `no-cache` dos chunks (README.md:309-312), o módulo `ops` e seu script root (README.md:313-317; docs/adr/009-modulo-ops.md), as portas e o loopback do core (CLAUDE.md:17; README.md:287-288), o Caddyfile compartilhado com `llmtrainer.likekiri.com` (CLAUDE.md:18-19; README.md:305-308; docs/adr/001-caddy.md), as versões do stack (docs/adr/002-stack-y-versiones.md:14-46), as sessões em Postgres e o cache do registry em memória (docs/adr/003-sin-redis.md:14-27), a configuração em `/etc/likekiri/` (docs/adr/004-ssr-islas-auth-y-despliegue.md:46-48) e o incidente de reload do Caddy (:52-57). ## Observações

**1. CLAUDE.md:3-5.** A frase resume a plataforma, e cada parte tem artefato. O core é o backend NestJS que a 3.4.3 julgou `No` como unidade frontend (linha apps/core). Os dez módulos têm build federado próprio e um servidor que publica o manifest em `/.well-known/module-manifest` (modules/hello/vite.config.ts:11-16; modules/hello/server.mjs:122-123). O site é o web-shell com SSR e ilhas, e o painel é a SPA do admin-shell (3.4.3; 3.4.5 Leitura). O README repete a abertura (README.md:3-9), assim como as `description` dos shells ("layout SSR + runtime de islas", apps/web-shell/package.json:5; "SPA del panel de administración", apps/admin-shell/package.json:5) e a apresentação das duas superfícies no guia (docs/como-integrar-un-modulo.md:11-18). Que o core "no conoce ningún dominio de negocio" é afirmação sobre o interior do core e não muda a leitura. "Independientes" tem aqui o sentido de processo, build e deploy próprios (3.4.6 #3-#12).

**2. CLAUDE.md:10-11.** O `grep -rn "modules/" apps/core/src` proposto pelo próprio texto volta vazio no snapshot, e o `package.json` do core só depende, entre os pacotes do workspace, de `@likekiri/contract` (apps/core/package.json:16). Os módulos entram pelo pull do manifest (apps/core/src/registry/registry.service.ts:401-420), a construção `remote-resolution` da 3.4.4. O core importa por `import()` o bundle SSR do web-shell, que é shell, não módulo (linha 19). A afirmação se repete na abertura do README ("se integran únicamente a través de un manifest firmado", README.md:3-5), no princípio da arquitetura (README.md:33-35, que acrescenta "le hace peticiones HTTP", ver linha 16), no guia (docs/como-integrar-un-modulo.md:3-4), no README e no `vite.config.ts` do `hello` (modules/hello/README.md:11-12; modules/hello/vite.config.ts:5-6) e no cabeçalho do servidor de `clientes` (modules/clientes/server.mjs:26).

**3. CLAUDE.md:12-13.** O core e os dez módulos dependem de `@likekiri/contract` (apps/core/package.json:16; ex.: modules/hello/package.json:12, modules/ops/package.json:8). O core o usa para assinar o pedido e verificar a resposta (apps/core/src/registry/registry.service.ts:402, :417), e cada `server.mjs` de módulo o importa para o mesmo fim (ex.: modules/hello/server.mjs:11). O README acrescenta que é "el único paquete que comparten el core y todos los módulos" (README.md:108). Isso confere: `@likekiri/tokens` e `@likekiri/i18n` só aparecem como dependência dos dois shells (linhas 11 e 33). O contrato é usado pela parte servidor dos módulos, não pelos componentes federados; os shells não dependem dele. Também repetem a afirmação CLAUDE.md:42, README.md:106-109, :174 e a `description` do pacote (packages/contract/package.json:4).

**4. CLAUDE.md:25-26.** O core carrega o bundle SSR do web-shell e executa o seu `render` no próprio processo (3.4.4, apps/core/src/shell/shell.service.ts:89 e :147), e a `description` do core diz o mesmo ("SSR del shell", apps/core/package.json:5). A hidratação acontece nas ilhas que chegam pré-renderizadas (`hydrateRoot`, apps/web-shell/src/islands.ts:63-65); as demais são montadas por `createRoot` (:67), e as páginas estáticas do shell nem recebem JavaScript (linha 40). "Hidratación" vale, então, para as ilhas, como precisa a árvore do README ("SSR en el core + hidratación de islas", README.md:159). O diagrama do README (README.md:53) também põe o SSR do shell no core.

**5. CLAUDE.md:27-29.** As únicas telas do admin-shell são `Login`, `AcceptInvite` e `ModulePage` (apps/admin-shell/src/App.tsx:15-17). O menu lateral é montado só com as entradas `sidebar` do manifest que o core devolve (apps/admin-shell/src/App.tsx:82-84, com o comentário "El sidebar se construye COMPLETO desde el manifest"), e as rotas de módulo vão para `ModulePage` (:214, :226). A 3.4.5 encontrou nove remotes consumidos pelo painel, todos por esse caminho (#1-#9). A afirmação se repete em README.md:8-9, :84-87, :160 e :327, no ADR 005 (docs/adr/005-admin-por-modulos-y-submenus.md:19-23), no guia (docs/como-integrar-un-modulo.md:17-18) e nos READMEs de `cuentas`, `registry` e `ejemplo-admin` ("el shell del admin no sabe que existe; lo descubre por el manifest", modules/cuentas/README.md:4-5; modules/registry/README.md:4-5; modules/ejemplo-admin/README.md:9-12).

**6. CLAUDE.md:31-32.** Os dois módulos declaram só rotas `admin` e um grupo de menu no `sidebar` com filhos: "Cuentas" (modules/cuentas/server.mjs:61-71) e "Plataforma" em `mode: 'toggle'` (modules/registry/server.mjs:48-57). A 3.4.5 os tem como remotes do painel (#3, #8). O ADR 005 conta a mudança: as telas saíram do shell para esses dois módulos (docs/adr/005-admin-por-modulos-y-submenus.md:25-31), e o guia os cita como exemplos de admin (linha 52). O modo do submenu de `cuentas` diverge entre ADR e código (ver Leitura), o que não muda a afirmação. A árvore do README repete os dois itens (README.md:163-164).

**7. CLAUDE.md:33-34.** `ejemplo-web` só declara rota `web` (modules/ejemplo-web/server.mjs:43), e `ejemplo-admin` só declara rotas `admin` (modules/ejemplo-admin/server.mjs:43, :49). A 3.4.5 tem um só como remote do site (#12) e o outro só como remote do painel (#4). Os arquivos estão de fato comentados como modelos (ex.: modules/ejemplo-web/vite.config.ts:5; modules/ejemplo-admin/server.mjs:13-17). Repetem a afirmação README.md:165-166, docs/como-integrar-un-modulo.md:6-7 e os READMEs dos dois módulos (modules/ejemplo-web/README.md:3-6; modules/ejemplo-admin/README.md:3-5).

**8. CLAUDE.md:35-37.** `clientes` declara três rotas `web` e duas `admin` (modules/clientes/server.mjs:1013-1017) e entra nos dois shells (3.4.5 #2, #11). O domínio próprio (API e SQLite no servidor do módulo, modules/clientes/server.mjs:54) é detalhe interno, que não muda a leitura. Repetem a afirmação README.md:167-168 (que acrescenta "SSR delegado", linha 20), modules/clientes/README.md:3-6, :30-38, docs/como-integrar-un-modulo.md:203-206 e a `description` do pacote (modules/clientes/package.json:5).

**9. CLAUDE.md:38-39.** A tela do módulo lê e grava a configuração pela API do core (`/api/admin/shell-config`, modules/sitio/src/SitioPage.tsx:22-32). O core lê essa configuração a cada render e a põe no pedido (apps/core/src/shell/shell.service.ts:130-131), e o web-shell desenha o header a partir dela (apps/web-shell/src/Document.tsx:41-44). O `sitio` entra no painel como remote (3.4.5 #9). A ligação com o site não é composição entre frontends: a página do módulo grava dados que o core injeta no SSR do shell. É o que dizem o comentário da própria tela (modules/sitio/src/SitioPage.tsx:5-8), o README do módulo (modules/sitio/README.md:3-24), o ADR 006 (docs/adr/006-server-driven-shell-y-tipo-de-cuenta.md:16-30) e README.md:125-130, que também chama a API de "plataforma" e o módulo de "solo la pantalla".

**10. CLAUDE.md:41.** O manifest do chat declara a rota `web` `/chat/widget` com `widget: true` e duas rotas `admin` com `./ChatAdminPage` (modules/chat/server.mjs:495-497). A 3.4.5 tem as duas relações (#1, #10). O WebSocket e a persistência são internos ao módulo. Repetem a afirmação README.md:171, modules/chat/README.md:3-5, :9-18, o cabeçalho do servidor (modules/chat/server.mjs:17-26) e a `description` do pacote (modules/chat/package.json:5).

**11. CLAUDE.md:43.** Os dois shells importam `cssVariables` de `@likekiri/tokens` e as injetam no seu CSS (apps/admin-shell/src/styles.ts:1, :10; apps/web-shell/src/styles.ts:1, :43); são duas unidades. A `description` do pacote diz "compartidos entre shells y módulos" (packages/tokens/package.json:4): nenhum módulo depende do pacote, mas componentes de seis módulos usam as variáveis `--lk-*` que o shell hospedeiro injeta (linha 57). Repetem a afirmação README.md:175 e o guia ("design tokens de `@likekiri/tokens`", docs/como-integrar-un-modulo.md:154-155).

O fim da frase diz que o acoplamento está "documentado en los README de los módulos", mas os READMEs dos módulos não o mencionam; ele aparece no guia (docs/como-integrar-un-modulo.md:154-156) e no comentário de `PanelPage` (modules/ejemplo-admin/src/PanelPage.tsx:11-12). Isso é sobre documentação, não sobre as unidades, e não muda o valor.

**46. docs/adr/006-server-driven-shell-y-tipo-de-cuenta.md:31-32.** O texto afirma que o circuito foi verificado em produção: uma linha gravada em `ShellSetting` aparece no render seguinte, e sem linha valem os padrões. O mecanismo está no código: o serviço de configuração cai nos padrões quando não há valor válido (apps/core/src/shell/shell-config.service.ts:39, :44), o core põe a configuração em cada pedido de render (apps/core/src/shell/shell.service.ts:130-131) e o web-shell desenha o header a partir dela (apps/web-shell/src/Document.tsx:41-44; linha 9). **47. docs/adr/007-ssr-delegado-al-modulo.md:20-23.** `clientes` tem dois builds: o SSR para `dist-ssr`, só com `react()`, sem federação, e o cliente federado (modules/clientes/vite.config.ts:11-24); o script roda os dois (modules/clientes/package.json:8). **48. docs/adr/007-ssr-delegado-al-modulo.md:31-33.** O teste em produção, com o formulário no HTML inicial e a degradação com o serviço parado, não tem artefato no snapshot. O mecanismo de degradação está no código (linha 20). Os testes do core existem (README.md:344-347), mas nenhuma revisão anterior os usou como evidência deste caso, e eles não substituem a verificação em produção que o texto afirma.

**49. docs/adr/007-ssr-delegado-al-modulo.md:52-53.** A afirmação é sobre o que as ilhas não compartilham, e é distinta do React singleton das linhas 21 e 37: a biblioteca é uma só, mas cada ilha tem a sua própria raiz React. O runtime monta cada ilha no seu elemento, por `hydrateRoot(spec.el, …)` ou `createRoot(spec.el)` (apps/web-shell/src/islands.ts:62-67), e não dentro da árvore React do shell, que é renderizada no servidor e não é hidratada no cliente (o bundle cliente só tem o runtime de ilhas, linha 41). A única entrada de dados de uma ilha são as props serializadas em `data-props` pelo SSR (apps/web-shell/src/entry-server.tsx:77-82) e lidas pelo runtime (apps/web-shell/src/islands.ts:30-32). No servidor, o HTML de um módulo entra como texto pronto (`dangerouslySetInnerHTML`, apps/web-shell/src/entry-server.tsx:93-97), não como componente dentro da árvore do shell, e o web-shell não declara contexto React (não há `createContext` nem `Provider` em `apps/web-shell/src`). As raízes separadas não deixam um contexto atravessar a fronteira. `corroborada`. A consequência listada antes, de que o primeiro render deve ser determinista para a hidratação (docs/adr/007-ssr-delegado-al-modulo.md:49-51), é detalhe interno dos componentes.

**50. docs/adr/007-ssr-delegado-al-modulo.md:54-55.** As três rotas `web` de `clientes` são `ssr: 'server'` (modules/clientes/server.mjs:1013-1015); as do `hello` e do `ejemplo-web` são `ssr: 'shell'` (modules/hello/server.mjs:45; modules/ejemplo-web/server.mjs:47).
