# 128 — fudoyoki/ai-portal-mfe-example

## Leitura do repositório

A documentação é o README da raiz, em inglês, o único arquivo `documentation` do `artifacts.csv`. Ele apresenta o projeto como exemplo completo de arquitetura de micro-frontends com Vite, React e Module Federation e um BFF NestJS (README.md:1-3), desenha a arquitetura num diagrama (README.md:7-36), dá a tabela de portas (README.md:38-49), o roteiro de execução local (README.md:51-127), a árvore de pastas comentada (README.md:131-144), os conceitos de federação e de pacotes compartilhados (README.md:146-183), o deploy para CDN (README.md:185-203), o SonarQube (README.md:205-214), como acrescentar um MFE (README.md:216-222), o Docker (README.md:224-274) e a tecnologia (README.md:276-283).

No que o README diz do shell e do dashboard, ele confere com as revisões anteriores: duas aplicações React/Vite num monorepo npm workspaces com Turborepo, o shell como host que carrega em runtime o `./DashboardApp` exposto pelo remote `mfeDashboard`, os pacotes `@ai-portal/ui-kit` e `@ai-portal/shared-types` declarados como `shared` singleton nos dois lados, e uma imagem Docker por aplicação. O README descreve, porém, um portal maior do que o snapshot: os remotes Chat, Tools e Admin só existem como linhas comentadas e placeholders no shell (apps/shell/vite.config.ts:32-35; apps/shell/src/App.tsx:150-158, 177-178), o BFF existe mas nenhuma unidade frontend o chama (apps/shell/src/context/AuthContext.tsx:14-34), o caminho de publicação no CDN não coincide com o que o shell espera (README.md:194-195; apps/shell/vite.config.ts:22) e os `sonar-project.properties` citados não estão no snapshot. Essas afirmações são `contradita`.

## Observações

**1. README.md:3.** O snapshot tem duas unidades frontend React com Vite e TypeScript, ligadas por `@originjs/vite-plugin-federation`, e um servidor NestJS em `apps/bff` (apps/bff/package.json:6-7, 16-18). O título (README.md:1), o subtítulo da página inicial "A micro-frontend architecture demo with Vite + React + Module Federation" (apps/shell/src/App.tsx:128) e as linhas "Frontend" e "BFF" do Tech Stack (README.md:278, 280) repetem a afirmação. "Complete" vale para o shell e o dashboard; o resto do portal desenhado está nas afirmações 3, 5 e 6.

**2. README.md:11-16.** O shell é o host: declara o remote `mfeDashboard` e o renderiza na rota `/dashboard/*` (apps/shell/vite.config.ts:28-31; apps/shell/src/App.tsx:165-176). As quatro responsabilidades do diagrama aparecem nele: autenticação (simulada) no `AuthProvider` montado em apps/shell/src/main.tsx:11-13, roteamento em `AppRoutes` (apps/shell/src/App.tsx:161-181), layout com cabeçalho, navegação e rodapé (apps/shell/src/App.tsx:57-118) e o estado do usuário, guardado no `AuthContext` com `useState` (apps/shell/src/context/AuthContext.tsx:15-16). O dashboard é o remote que se publica como `mfeDashboard` (apps/mfe-dashboard/vite.config.ts:11-17). Repetem a afirmação as linhas "Shell \| 3000 \| Host container" e "MFE Dashboard \| 3001 \| Analytics & widgets" (README.md:42-43), os comentários da árvore "Host container (port 3000)" e "Dashboard MFE (port 3001)" (README.md:136-137) e os comentários "Shell - Host container" e "MFE Dashboard" do compose (docker-compose.yml:4, 18).

**3. README.md:14-16.** O diagrama põe Chat e Tools como remotes ao lado do Dashboard, mas o snapshot não tem diretório nem configuração ativa para eles: as entradas `mfeChat` e `mfeTools` estão comentadas sob "Add more MFEs as they're created" (apps/shell/vite.config.ts:32-34), e as rotas `/chat/*` e `/tools/*` renderizam o `ComingSoon` local do shell, comentado como "Placeholder for MFEs not yet implemented" (apps/shell/src/App.tsx:150-158, 177-178). Só existem como declarações de tipo (apps/shell/src/vite-env.d.ts:10-20), como serviço `mfe-chat` comentado (docker-compose.yml:29-37) e como origens CORS do BFF (apps/bff/src/main.ts:15-16). A parte confirmada da figura, o Dashboard como remote, é a afirmação 2. As linhas "MFE Chat" e "MFE Tools" da tabela de portas (README.md:44-45) repetem esta afirmação.

**4. README.md:21-22.** Os dois pacotes são declarados como `shared` singleton tanto no shell quanto no dashboard (apps/shell/vite.config.ts:53-58; apps/mfe-dashboard/vite.config.ts:33-38), e as duas unidades usam os dois: `ui-kit` no `Spinner` do shell e no `Card` e `Button` do dashboard (apps/shell/src/App.tsx:3; apps/mfe-dashboard/src/DashboardApp.tsx:2), `shared-types` no `AuthContext` do shell e no `DashboardApp` (apps/shell/src/context/AuthContext.tsx:2; apps/mfe-dashboard/src/DashboardApp.tsx:3). O uso de `shared-types` é só de tipos (`import type`), sem código em runtime, de modo que o compartilhamento pela federação só tem efeito para `ui-kit`. Repetem a afirmação os comentários da árvore "Shared UI components" e "Shared TypeScript types" (README.md:140-141), o comentário "This package is installed on the Shell and shared via Module Federation" (packages/ui-kit/src/index.ts:1-2) e "Share the UI kit - MFEs won't bundle their own copy" (apps/shell/vite.config.ts:52).

**5. README.md:25-30.** O diagrama liga a caixa do navegador, onde estão o shell e os MFEs, ao BFF, com as rotas `/api/auth` e `/api/chat`. O BFF existe com essas rotas (prefixo `api` em apps/bff/src/main.ts:23; controladores `auth` e `chat` em apps/bff/src/auth/auth.controller.ts:5 e apps/bff/src/chat/chat.controller.ts:9), mas nenhuma unidade frontend o chama: não há `fetch` nem cliente HTTP em `apps/shell/src` e `apps/mfe-dashboard/src`, e o `AuthContext` do shell usa um usuário fictício, com os comentários "In real app: redirect to BFF /api/auth/login" e "In real app: call BFF /api/auth/logout" no lugar das chamadas (apps/shell/src/context/AuthContext.tsx:6-34). A parte que se confirma é a existência do BFF com essas rotas; a ligação das unidades com ele é desmentida pelo próprio código. O próprio README marca o BFF como "(optional)" no roteiro (README.md:92). A linha "BFF \| 4000 \| API gateway" (README.md:47) e o comentário "BFF - Backend for Frontend" (docker-compose.yml:39) repetem a afirmação; o `depends_on` do shell sobre o `bff` no compose só ordena a subida dos contêineres (docker-compose.yml:11-13).

**6. README.md:46.** A tabela de portas lista um MFE Admin com porta e papel. No snapshot ele não tem diretório, o remote `mfeAdmin` está comentado sob "Add more MFEs as they're created" (apps/shell/vite.config.ts:32, 35), e o shell não tem nem item de navegação nem rota para ele (apps/shell/src/App.tsx:61-66, 165-179); só restam a declaração de tipo (apps/shell/src/vite-env.d.ts:22-26) e a origem CORS do BFF (apps/bff/src/main.ts:17).

**7. README.md:61.** O passo exige construir `shared-types` e `ui-kit` antes das aplicações. As duas aplicações dependem dos dois pacotes (apps/shell/package.json:14-15; apps/mfe-dashboard/package.json:14-15), a task `build` do Turbo depende do build dos pacotes de que cada app depende (turbo.json:4-6), e os dois Dockerfiles constroem os pacotes antes do app, com o comentário "Build shared packages first, then shell" / "then MFE" (apps/shell/Dockerfile:17-20; apps/mfe-dashboard/Dockerfile:17-20). A tabela "Rebuilding After Changes" repete a dependência: "Rebuild it → rebuild all apps that depend on it" para `shared-types` e "Rebuild it → rebuild MFEs → restart MFE previews" para `ui-kit` (README.md:123-124). Essa segunda instrução supõe que o build dos MFEs carrega o `ui-kit`, o que fica em tensão com a afirmação 13.

**8. README.md:70.** O snapshot confirma que o remote é configurado para gerar `remoteEntry.js` (apps/mfe-dashboard/vite.config.ts:12-13), que o shell, em desenvolvimento, o busca em `http://localhost:3001/assets/remoteEntry.js` (apps/shell/vite.config.ts:17-19), e que o dashboard tem `build` e `preview` na mesma porta 3001 (apps/mfe-dashboard/package.json:8-9; apps/mfe-dashboard/vite.config.ts:47-50). Que o plugin só gere o arquivo no build, e não no `vite` de desenvolvimento, é comportamento da ferramenta, sem artefato no snapshot. A explicação "Vite Module Federation generates `remoteEntry.js` only at **build time**. So MFEs must be: 1. **Built** […] 2. **Previewed**" (README.md:111-113) e a linha "`apps/mfe-dashboard` \| Rebuild → restart preview" (README.md:125) repetem a afirmação. O `docker-compose.dev.yml`, ao contrário do README, sobe o dashboard com `npm run dev` (docker-compose.dev.yml:27); pela afirmação, esse ambiente não serviria o `remoteEntry.js` ao shell, mas isso também é comportamento da ferramenta.

**9. README.md:103.** O shell renderiza o `DashboardApp` remoto dentro do seu layout, na rota `/dashboard/*`, envolvido por `MfeErrorBoundary` e `Suspense` (apps/shell/src/App.tsx:167-176, 184-189). O aviso do modo standalone, "In production, this MFE is loaded into the Shell." (apps/mfe-dashboard/src/main.tsx:21), repete a afirmação.

**10. README.md:115.** A configuração de federação do shell só declara `remotes`, sem `exposes` (apps/shell/vite.config.ts:28-36), enquanto o dashboard expõe `./DashboardApp` (apps/mfe-dashboard/vite.config.ts:15-17). O shell, como host, pode rodar no servidor de desenvolvimento, porque é ele que consome o arquivo gerado pelo remote; o remote precisa estar construído (afirmação 8).

**11. README.md:142-143.** O `package.json` da raiz declara os workspaces `apps/*` e `packages/*` e delega os scripts a `turbo run` (package.json:5-15), e o `turbo.json` define as tasks (turbo.json:3-25). A revisão de dependências registrou `turbo` como `Undetermined`, porque só os scripts do `package.json` o invocam, mas a afirmação, de que o arquivo é a configuração do Turborepo, se confirma. "**Monorepo:** Turborepo + npm workspaces" (README.md:281) repete a afirmação.

**12. README.md:150.** O dashboard expõe `./DashboardApp` (apps/mfe-dashboard/vite.config.ts:15-17), e o shell o importa com `React.lazy(() => import('mfeDashboard/DashboardApp'))` (apps/shell/src/App.tsx:7), carregando o `remoteEntry.js` pela URL do remote (apps/shell/vite.config.ts:17-23, 30-31). Repetem a afirmação os comentários "Lazy load MFEs - they're loaded from remote servers at runtime" (apps/shell/src/App.tsx:6), "Expose components that Shell can load" (apps/mfe-dashboard/vite.config.ts:14), "Main exported component - this is what the Shell imports" (apps/mfe-dashboard/src/DashboardApp.tsx:88) e "When loaded via Shell, DashboardApp is imported directly" (apps/mfe-dashboard/src/main.tsx:8).

**13.
