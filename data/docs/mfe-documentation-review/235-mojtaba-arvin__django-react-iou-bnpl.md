## Observações

**1. README.md:10.** A revisão estrutural registrou três unidades frontend, um shell e dois remotes, e a de composição, duas relações host → remote ativas por Module Federation (frontend/shell/webpack.config.js:59-64). A frase fala do sistema inteiro, com backend Django; a arquitetura de micro-frontends vale só para o frontend. O badge (README.md:6) repete a afirmação.

**2. README.md:12.** Cada remote devolve uma configuração do `AdminApp`, componente react-admin da biblioteca comum (frontend/customer-app/src/application/services/create-admin-app-config.service.ts:7-25; frontend/merchant-app/src/application/services/create-admin-app-config.service.ts:8-23), e o shell monta cada uma num `AdminApp` próprio, sob `${customerBasePath}/*` e `${merchantBasePath}/*` (frontend/shell/src/infrastructure/shell/shell-app.bootstrap.tsx:47-66), que valem `/customer` e `/merchant` (frontend/shared/src/infrastructure/context/global-settings.context.tsx:30-31). São dois painéis separados, um por remote. A afirmação se repete em README.md:232-233 e nos endereços do roteiro de demonstração (ex.: README.md:413, 422). A segunda parte da frase, a restrição de login por tipo de conta, é detalhe interno e ficou fora.

**3. README.md:42.** O shell declara os dois remotes no `ModuleFederationPlugin` do próprio webpack 5 (frontend/shell/webpack.config.js:3, 59-64) e os carrega com `import()` em tempo de execução (frontend/shell/src/infrastructure/shell/remote-modules/customer-app.adapter.ts:10; frontend/shell/src/infrastructure/shell/remote-modules/merchant-app.adapter.ts:10). O que se carrega não é um app React pronto, mas uma fábrica que devolve as telas da área para o `AdminApp` comum (3.4.4, Notas); os apps são independentes no sentido de que cada um tem manifesto, entrada, build e servidor de desenvolvimento próprios (3.4.3; frontend/customer-app/package.json:6-9) e de que não importam o código-fonte uns dos outros (classificação, "Código-fonte (fronteiras)"). Os três dependem da mesma biblioteca de workspace, `@bnpl/shared`, integrada em build time (afirmação 6). Isso confirma o desenvolvimento em paralelo no sentido técnico; o snapshot não diz nada sobre equipes, e o histórico tem um só autor (classificação, "Autoria e histórico"). Repetição: "Micro-Frontend | Webpack 5, Module Federation | Runtime dynamic module loading" (README.md:391).

**4. README.md:42.** A revisão de build e deploy registrou deploy `não observado` para as três aplicações (3.4.6 #1-#3). O único contêiner do frontend é um ambiente de desenvolvimento comum aos quatro pacotes, que não copia o código nem faz build (frontend/Dockerfile.dev:15, 52; docker-compose.dev.yml:149-174), e os dois workflows tratam só do backend. Nada no snapshot implanta as unidades, nem juntas nem em separado. Os builds são separados, cada um com seu `dist` e seu `remoteEntry.js` (3.4.6 #1-#3), o que permitiria deploys isolados, mas não os mostra.

**5. README.md:245-261.** Cada remote tem os scripts `dev:standalone` e `build:standalone` (frontend/customer-app/package.json:8-9; frontend/merchant-app/package.json:8-9), que escolhem no `webpack.config.js` uma entrada própria com `HtmlWebpackPlugin` (frontend/customer-app/webpack.config.js:14-18, 74-79), e essa entrada monta a área com `renderStandaloneApp` (frontend/customer-app/src/infrastructure/standalone/standalone-app.bootstrap.tsx:4-8; frontend/shared/src/infrastructure/standalone/standalone-app.bootstrap.tsx:36-42). As portas citadas, 3001 e 3002, são as dos `devServer` (frontend/customer-app/webpack.config.js:121; frontend/merchant-app/webpack.config.js:121). Os comandos do README trocam os filtros: o de "customer standalone" filtra `@bnpl/merchant-app` (README.md:250), e o de "merchant standalone", `@bnpl/customer-app` (README.md:258), como a classificação já anotou; é erro de instrução, e os scripts existem nos dois pacotes. O shell não tem modo standalone, e o README não diz que tem.

**6. README.md:360-369.** A árvore lista os quatro pacotes do workspace (frontend/pnpm-workspace.yaml:1-5) com os papéis que as revisões registraram: o shell como host e customer-app e merchant-app como remotes (3.4.5 #1, #2), e `shared` como biblioteca, que a revisão estrutural não conta como unidade. "Shared" se confirma: as três unidades declaram `"@bnpl/shared": "workspace:*"` (frontend/shell/package.json:11-13; frontend/customer-app/package.json:13-15; frontend/merchant-app/package.json:14-16), resolvem o pacote por alias de webpack (frontend/shell/webpack.config.js:37; frontend/customer-app/webpack.config.js:35) e o importam no código (ex.: frontend/shell/src/infrastructure/shell/remote-modules/customer-app.adapter.ts:1-5; frontend/customer-app/src/application/services/create-admin-app-config.service.ts:1-2). **7. README.md:397.** `frontend/pnpm-workspace.yaml:1-5` declara os quatro pacotes, e a raiz repete a lista em `workspaces` (frontend/package.json:5-10). A árvore da afirmação 6 também cita o `pnpm-workspace.yaml` (README.md:367).

**8. frontend/customer-app/webpack.config.js:13.** O comentário explica a escolha da entrada (:14-22): só a entrada standalone chama `root.render`; no modo remoto, a entrada é um arquivo vazio (`remote-entry.module.ts`, 0 bytes; 3.4.3, Notas), o remote expõe só a fábrica de configuração (:85-88), e quem renderiza é o shell, com o `AdminApp` que recebe a configuração (frontend/shell/src/infrastructure/shell/shell-app.bootstrap.tsx:52, 62) dentro da única raiz React, criada na entrada do shell (:81-82). O comentário de :84, "No root.render files to prevent multi React Trees in shell", repete a afirmação e dá o motivo. Os dois comentários estão também em frontend/merchant-app/webpack.config.js:13 e :84, cuja configuração só difere pelo `name`, pela porta e pelo `publicPath` standalone. A frase menciona primeiro qual entrada pode renderizar, o que é a divisão de papéis entre shell e remote; por isso o tema é composição.

**9. frontend/package.json:70.** O campo documenta `@module-federation/typescript` dizendo que o webpack precisa do `ModuleFederationPlugin` para fornecer e consumir módulos em runtime. A parte do runtime se confirma: as três configurações usam o plugin, com `remotes` no shell e `exposes` nos remotes (3.4.5 #1, #2). A atribuição do plugin ao pacote é desmentida: os três `webpack.config.js` obtêm o `ModuleFederationPlugin` de `require("webpack").container` (frontend/shell/webpack.config.js:3; frontend/customer-app/webpack.config.js:3; frontend/merchant-app/webpack.config.js:3), e o pacote só aparece como plugin do compilador TypeScript em `frontend/shell/tsconfig.build.json:17-24`, sem efeito confirmado no build (3.4.2, `Undetermined`).

**10. frontend/shell/src/infrastructure/shell/shell-app.bootstrap.tsx:21-24.** O componente `App` carrega as duas configurações na montagem (:34-37), espera as duas antes de renderizar (:39-41) e monta cada `AdminApp` dentro de `ErrorBoundary` e `Suspense` nas rotas das duas áreas (:45-66), o que as revisões de código-fonte e de composição registraram. As promessas de :35-36 não têm `catch`, e o `ErrorBoundary` em volta do `AdminApp` não cobre uma falha nesse carregamento (classificação, Notas); o comentário diz que as configurações são envolvidas, e são, mas isso não protege a carga em si.
