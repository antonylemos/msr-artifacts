## Leitura do repositório

Cópia do monorepo `openmrs-esm-patient-chart`. É um workspace Yarn 4 com `packages/*` (package.json:5-7, :87), e o Turborepo executa a tarefa `build` de cada pacote, com saída em `dist/**` (turbo.json:4-11). Cada um dos 18 apps tem script `build` próprio. Nos 17 apps React é `webpack --mode production` sobre a configuração padrão `openmrs/default-webpack-config`, que é um pacote externo e não está no snapshot (ex.: packages/esm-patient-chart-app/package.json:13; packages/esm-patient-chart-app/webpack.config.js:1). No app Angular é `ng build` (packages/esm-form-entry-app/package.json:13). Cada pacote declara como saída um bundle com o próprio nome em `dist/` (ex.: packages/esm-patient-chart-app/package.json:6). A biblioteca `packages/esm-patient-common-lib` também é pacote do workspace, mas a revisão estrutural não a conta como aplicação.

A forma de publicação é a do OpenMRS 3: cada app vira um pacote npm `@openmrs/esm-*-app`, e um app shell externo junta esses pacotes numa SPA. No CI (.github/workflows/ci.yml), o job `build` roda `yarn verify` e o build de todos os pacotes em push e pull request (.github/workflows/ci.yml:3-10, :48-52). O `pre_release`, em push, aplica a todos os pacotes a mesma versão `-pre.<run>`, constrói e publica com a tag `next` (`ci:prepublish`) (.github/workflows/ci.yml:86-90, :97-100; package.json:11). O `release`, numa release do GitHub, constrói e publica com a tag `latest` (`ci:publish`) no registry `https://registry.npmjs.org` (.github/workflows/ci.yml:126-131, :139, :158-162; package.json:10). Os dois scripts rodam `npm publish --access public` em cada workspace, exceto na raiz (package.json:10-11). Cada app sai, portanto, num pacote próprio, com nome e versão próprios. O script `release` sobe a versão de todos os pacotes juntos (package.json:13), e no snapshot todos estão em `10.2.0`, a mesma da raiz (package.json:4; ex.: packages/esm-patient-chart-app/package.json:3). O versionamento é próprio de cada pacote e usado na publicação, mas avança em bloco. Depois do pré-release, o job `deploy_patient_chart` só dispara por HTTP um plano do Bamboo do OpenMRS, que reconstrói a aplicação de referência fora do repositório (.github/workflows/ci.yml:110-124). O job também guarda os `dist` como artefato do workflow (.github/workflows/ci.yml:102-108). O `bundle-size.yml` só mede o tamanho do build nos pull requests (.github/workflows/bundle-size.yml:28-33).

Os artefatos Docker do snapshot são de teste e2e, não de publicação. No workflow `e2e.yml`, depois do build (.github/workflows/e2e.yml:65-66), o script `run-e2e-docker-env.sh` empacota com `yarn pack` cada workspace com `-app` no caminho, exceto o `esm-form-entry-app` (e2e/support/github/run-e2e-docker-env.sh:8, :14-22). Em seguida, gera um `spa-assemble-config.json` com esses pacotes mais os módulos externos de navegação e home (e2e/support/github/run-e2e-docker-env.sh:29-38) e sobe o compose num diretório temporário (e2e/support/github/run-e2e-docker-env.sh:42-49). O Dockerfile monta a SPA com `openmrs assemble` (e2e/support/github/Dockerfile:9-13) e a serve numa imagem nginx que reaproveita a configuração da imagem `openmrs-reference-application-3-frontend:nightly` (e2e/support/github/Dockerfile:15-32). O compose a expõe em `SPA_PATH: /openmrs/spa`, atrás do gateway na porta 8080, com backend e banco de dados de imagens prontas (e2e/support/github/docker-compose.yml:5-24). Os testes Playwright rodam contra esse ambiente, que é derrubado no fim (.github/workflows/e2e.yml:68-79). Essa imagem junta os 17 apps, mas existe só para os testes, por isso não decide a coluna Deploy. O compose do Bamboo não constrói nada do repositório: usa a imagem nightly do frontend de referência e as de gateway, backend e banco (e2e/support/bamboo/docker-compose.yml:20-53), mais um contêiner Playwright (e2e/support/bamboo/docker-compose.yml:5-16; e2e/support/bamboo/playwright.Dockerfile:2) que roda os testes (e2e/support/bamboo/e2e-test-runner.sh:3-13).

Os demais workflows não constroem nem publicam aplicação: `tx-pull.yml` e `tx-push.yml` sincronizam traduções com o Transifex (.github/workflows/tx-pull.yml:20-21; .github/workflows/tx-push.yml:18-19), e `update-openmrs-deps.yml` abre PRs de atualização de dependências OpenMRS (.github/workflows/update-openmrs-deps.yml:33-37).
