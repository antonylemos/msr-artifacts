# 060 — hscale/adx-core-k

## Leitura do repositório

Plataforma de exemplo ("ADX CORE") com backend Rust, BFFs em Node e sete aplicações React/Vite em `adx-core/apps/`: um shell e seis remotes de Module Federation. Cada aplicação tem `vite.config.ts` e script `build` próprios (`tsc && vite build`, ex.: adx-core/apps/auth/package.json:8). O manifesto da raiz declara um workspace com `apps/*`, `packages/*`, `bff-services/*` e `tools/*` e dispara os builds de todos os membros com `yarn workspaces run build` (package.json:5-10, 14). Esses padrões são relativos à raiz. As aplicações estão em `adx-core/apps/`, e não há `package.json` em `adx-core/`, então o workspace não alcança nenhuma delas (ver a revisão estrutural). O `package-workspace.json` da raiz tem scripts `build:shell` e `build:apps`, mas `build:apps` só constrói o shell (package-workspace.json:19-22). Os scripts `dev:<remote>` desse arquivo só imprimem "not yet implemented" (package-workspace.json:13-18). Como não é um `package.json`, nenhum comando o usa.

Dois workflows do GitHub Actions publicam as aplicações uma a uma no S3, atrás do CloudFront. O `deploy-microfrontends.yml` tem um job em matriz, uma entrada por aplicação (`shell,auth,tenant,file,user,workflow,module`, .github/workflows/deploy-microfrontends.yml:45, 53, 67, 73-75). Cada entrada roda o build da aplicação (:105-111), confere o `remoteEntry.js` dos remotes (:138-142) e sincroniza o `dist` num caminho próprio do bucket: o shell em `<ambiente>/` e cada remote em `<ambiente>/apps/<app>/` (:151-170). Depois invalida no CloudFront só o caminho daquela aplicação (:172-184) e grava um registro por aplicação em `deployments/<app>-latest.json` (:186-207). O `deploy-production.yml` faz o mesmo em dois jobs, um que constrói (`build-frontend-apps`, :208-236) e outro que publica (`deploy-frontend-apps`, :305-335), em `s3://adx-core-frontend-<ambiente>/<app>/` (:329). A matriz desse workflow tem seis aplicações, sem `module` (:213, 311). O `automated-rollback.yml` deixa reverter cada aplicação pelo nome (.github/workflows/automated-rollback.yml:17-39). Ele chama scripts/deployment-rollback.sh, que restaura cada aplicação no caminho dela, `<ambiente>/` ou `<ambiente>/apps/<app>/` (scripts/deployment-rollback.sh:171-175, 205-219).

Esses workflows não correspondem ao snapshot. Todos usam `apps/<app>`, sem o prefixo `adx-core/`: nos gatilhos (.github/workflows/deploy-microfrontends.yml:7-8; .github/workflows/deploy-production.yml:87-104), no build (`npm run build --workspace=apps/<app>`, .github/workflows/deploy-microfrontends.yml:108, 110) e no diretório de saída (`apps/<app>/dist`, :119, 121, 154, 157; .github/workflows/deploy-production.yml:236). O `deploy-production.yml` chama `npm run build:<app>` (:228), que não existe no package.json da raiz (package.json:11-17). Os dois instalam com `npm ci` (.github/workflows/deploy-microfrontends.yml:89; .github/workflows/deploy-production.yml:225) a partir de um workspace que não inclui `adx-core/apps/*`. Do jeito que estão, não constroem nem publicam as aplicações deste snapshot. Também não há produção configurada para a composição: o shell aponta os seis remotes para `http://localhost:300N/assets/remoteEntry.js` (adx-core/apps/shell/vite.config.ts:11-18), e nenhum `vite.config.ts` define `base` para os subcaminhos `/apps/<app>/` em que os remotes seriam publicados (não há ocorrência `cfg-public-path`). O guia adx-core/docs/developer-guide/module-federation.md:56-72 descreve endereços de remote lidos de `window.<app>AppUrl`, mas a configuração do snapshot não faz isso. Isso é documentação e não entra na coluna Deploy.

O resto da infraestrutura é de backend. O `deploy-microservices.yml` e os jobs de backend e BFF do `deploy-production.yml` geram imagens e as aplicam no Kubernetes (.github/workflows/deploy-microservices.yml:6-9, 80-125, 261-311; .github/workflows/deploy-production.yml:124-206, 238-303). O `ci.yml` compila o workspace Rust e publica imagens de três serviços (.github/workflows/ci.yml:76-78, 136-185). O `comprehensive-tests.yml` sobe a infraestrutura de desenvolvimento e roda `npm run dev:all` para os testes E2E (.github/workflows/comprehensive-tests.yml:172-177, 219-222), um uso de desenvolvimento. O `mobile-tests.yml` e o `tauri-desktop-tests.yml` disparam em `apps/**` e empacotam builds de teste com Tauri (.github/workflows/mobile-tests.yml:6-7, 50-51, 124-125; .github/workflows/tauri-desktop-tests.yml:6-7, 70-80, 107-112). Os scripts `build:mobile:*` e `build:desktop` não existem no package.json da raiz, e não há `src-tauri/` no snapshot. Os compose de adx-core/infrastructure/docker/ (`dev`, `prod`, `database`, `temporal`) e de adx-core/infrastructure/production/ declaram bancos, Temporal, observabilidade, serviços Rust, BFFs e nginx (ex.: adx-core/infrastructure/docker/docker-compose.prod.yml:101-102, 261-262, 409-420; adx-core/infrastructure/production/docker-compose.prod.yml:84-87, 311-324). Nenhum serviço é frontend. O adx-core/infrastructure/docker/Dockerfile.db-migrator constrói o migrador Rust do banco (:1-2, 37; adx-core/infrastructure/docker/docker-compose.database.yml:97-100). O adx-core/infrastructure/production/nginx/nginx.conf só faz proxy para API gateway, serviços, métricas e ferramentas de monitoramento (:115-202, 229-248). Não serve arquivos estáticos de nenhuma aplicação. Seu `location /auth/` encaminha para o `auth_service` do backend (:142-145). As ocorrências `cors` estão nos servidores de desenvolvimento do Vite (ex.: adx-core/apps/shell/vite.config.ts:60-63; adx-core/apps/file/vite.config.ts:28). As ocorrências `ops-hosting` em adx-core/docs/ e em tests/README.md são documentação.

## Observações

**1. adx-core/apps/auth.** O build é separado: configuração Vite e script próprios, e o `dist` da aplicação gera seu próprio `remoteEntry.js` (adx-core/apps/auth/vite.config.ts:9-12). Os dois workflows publicam a aplicação à parte, num caminho próprio do bucket e com invalidação própria no CloudFront. Isso sustentaria `separado`. Mas os workflows constroem e copiam `apps/auth`, que não existe no snapshot (a aplicação está em `adx-core/apps/auth`), e instalam a partir de um workspace que não a inclui. Não dá para estabelecer que o artefato cobre esta aplicação ou que está em uso, então o Deploy fica `Undetermined`. O registro de deploy guarda `version: github.sha` por aplicação (.github/workflows/deploy-microfrontends.yml:189-193). É o commit do repositório inteiro, não uma versão da aplicação. A `version: 1.0.0` do manifesto (adx-core/apps/auth/package.json:3) não é usada na publicação. Versionamento `No`.

**2. adx-core/apps/file.** Mesmo arranjo do auth, com o caminho `apps/file` nos workflows. O build próprio referencia, nos exposes, componentes que não estão no snapshot (adx-core/apps/file/vite.config.ts:13-15). O passo de verificação do workflow exige `index.html` no `dist` (.github/workflows/deploy-microfrontends.yml:129-132), e a pasta não tem `index.html` (ver a revisão estrutural). Mesmo com o caminho corrigido, a publicação falharia nesse passo.

**3. adx-core/apps/module.** Mesmo arranjo, mas só o `deploy-microfrontends.yml` cobre o `module` (.github/workflows/deploy-microfrontends.yml:45, 53). A matriz do `deploy-production.yml` não o inclui (.github/workflows/deploy-production.yml:213, 311). O rollback o lista entre as aplicações (scripts/deployment-rollback.sh:175). O build próprio depende de arquivos ausentes do snapshot: exposes em adx-core/apps/module/vite.config.ts:15-17 e o `./index.css` importado em adx-core/apps/module/src/main.tsx:4.

**4. adx-core/apps/shell.** Build próprio. Os workflows o publicam na raiz do ambiente, `<ambiente>/` (.github/workflows/deploy-microfrontends.yml:153-155), e invalidam `/<ambiente>/*` (:174-178), que inclui os caminhos dos remotes. O `deploy-production.yml` o publica em `shell/`, como os demais (:329). Os dois workflows não concordam sobre onde o shell fica em relação aos remotes. A mesma divergência de caminho `apps/shell` vale aqui. Mesmo publicado, o shell carregaria os remotes de `localhost` (adx-core/apps/shell/vite.config.ts:11-18): não há, no snapshot, configuração que ligue o shell aos endereços publicados dos remotes. Só o `package-workspace.json` tem um `build:shell` (package-workspace.json:22), e ele não é usado. Sem versão própria.

**5. adx-core/apps/tenant.** Mesmo arranjo do auth, caminho `apps/tenant`. O expose `./TenantSwitcher` aponta para arquivo ausente (adx-core/apps/tenant/vite.config.ts:13), e a pasta não tem `index.html`, exigido pela verificação do workflow (.github/workflows/deploy-microfrontends.yml:129-132).

**6. adx-core/apps/user.** Igual ao `file`: build próprio com exposes ausentes (adx-core/apps/user/vite.config.ts:13-15), sem `index.html`, e workflows com o caminho `apps/user`.

**7. adx-core/apps/workflow.** Igual ao `file`: build próprio com exposes ausentes (adx-core/apps/workflow/vite.config.ts:13-15), sem `index.html`, e workflows com o caminho `apps/workflow`.
