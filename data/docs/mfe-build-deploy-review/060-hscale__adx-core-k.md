# 060 — hscale/adx-core-k

## Repository overview

Example platform ("ADX CORE") with Rust backend, Node BFFs and seven React/Vite applications in `adx-core/apps/`: a shell and six Module Federation remotes. Each application has its own `vite.config.ts` and `build` script (`tsc && vite build`, for example: adx-core/apps/auth/package.json:8). Root manifest declares a workspace with `apps/*`, `packages/*`, `bff-services/*` and `tools/*` and triggers all members’ builds with `yarn workspaces run build` (package.json:5-10, 14). These patterns are root-relative. Applications are in `adx-core/apps/`, and there is no `package.json` in `adx-core/`, so the workspace reaches none of them (see the structural review). Root `package-workspace.json` has `build:shell` and `build:apps` scripts, but `build:apps` builds only shell (package-workspace.json:19-22). Its `dev:<remote>` scripts only print "not yet implemented" (package-workspace.json:13-18). Since it is not a `package.json`, no command uses it.

Two GitHub Actions workflows publish applications individually to S3 behind CloudFront. The `deploy-microfrontends.yml` has a matrix job, one entry per application (`shell,auth,tenant,file,user,workflow,module`, .github/workflows/deploy-microfrontends.yml:45, 53, 67, 73-75). Each entry runs application build (:105-111), checks remote `remoteEntry.js` (:138-142) and syncs `dist` to its own bucket path: shell at `<ambiente>/` and each remote at `<ambiente>/apps/<app>/` (:151-170). Then invalidates only that application’s path in CloudFront (:172-184) and writes a per-application record at `deployments/<app>-latest.json` (:186-207). The `deploy-production.yml` does the same in two jobs, one building (`build-frontend-apps`, :208-236) and one publishing (`deploy-frontend-apps`, :305-335), at `s3://adx-core-frontend-<ambiente>/<app>/` (:329). That workflow matrix has six applications, without `module` (:213, 311). The `automated-rollback.yml` allows reverting each application by name (.github/workflows/automated-rollback.yml:17-39). It calls scripts/deployment-rollback.sh, restoring each application at its path, `<ambiente>/` or `<ambiente>/apps/<app>/` (scripts/deployment-rollback.sh:171-175, 205-219).

These workflows do not match the snapshot. All use `apps/<app>` without prefix `adx-core/`: in triggers (.github/workflows/deploy-microfrontends.yml:7-8; .github/workflows/deploy-production.yml:87-104), build (`npm run build --workspace=apps/<app>`, .github/workflows/deploy-microfrontends.yml:108, 110) and output directory (`apps/<app>/dist`, :119, 121, 154, 157; .github/workflows/deploy-production.yml:236). The `deploy-production.yml` calls `npm run build:<app>` (:228), absent from root package.json (package.json:11-17). Both install with `npm ci` (.github/workflows/deploy-microfrontends.yml:89; .github/workflows/deploy-production.yml:225) from a workspace excluding `adx-core/apps/*`. As written, they neither build nor publish this snapshot’s applications. Production composition is also unconfigured: shell points all six remotes to `http://localhost:300N/assets/remoteEntry.js` (adx-core/apps/shell/vite.config.ts:11-18), and no `vite.config.ts` defines `base` for subpaths `/apps/<app>/` where remotes would be published (no `cfg-public-path` occurrence). Guide adx-core/docs/developer-guide/module-federation.md:56-72 describes remote addresses read from `window.<app>AppUrl`, but snapshot configuration does not do this. That is documentation and does not enter Deploy.

The remaining infrastructure is backend. The `deploy-microservices.yml` and backend and BFF jobs in `deploy-production.yml` generate images and apply them in Kubernetes (.github/workflows/deploy-microservices.yml:6-9, 80-125, 261-311; .github/workflows/deploy-production.yml:124-206, 238-303). The `ci.yml` compiles the Rust workspace and publishes images of three services (.github/workflows/ci.yml:76-78, 136-185). The `comprehensive-tests.yml` starts development infrastructure and runs `npm run dev:all` for E2E tests (.github/workflows/comprehensive-tests.yml:172-177, 219-222), a development use. The `mobile-tests.yml` and `tauri-desktop-tests.yml` trigger on `apps/**` and package test builds with Tauri (.github/workflows/mobile-tests.yml:6-7, 50-51, 124-125; .github/workflows/tauri-desktop-tests.yml:6-7, 70-80, 107-112). Scripts `build:mobile:*` and `build:desktop` do not exist in root package.json, and no `src-tauri/` is in the snapshot. Compose files in adx-core/infrastructure/docker/ (`dev`, `prod`, `database`, `temporal`) and adx-core/infrastructure/production/ declare databases, Temporal, observability, Rust services, BFFs and nginx (for example: adx-core/infrastructure/docker/docker-compose.prod.yml:101-102, 261-262, 409-420; adx-core/infrastructure/production/docker-compose.prod.yml:84-87, 311-324). No service is frontend. The adx-core/infrastructure/docker/Dockerfile.db-migrator builds the Rust database migrator (:1-2, 37; adx-core/infrastructure/docker/docker-compose.database.yml:97-100). The adx-core/infrastructure/production/nginx/nginx.conf only proxies API gateway, services, metrics and monitoring tools (:115-202, 229-248). It serves no application’s static files. Its `location /auth/` forwards to backend `auth_service` (:142-145). The `cors` occurrences are in Vite development servers (for example: adx-core/apps/shell/vite.config.ts:60-63; adx-core/apps/file/vite.config.ts:28). The `ops-hosting` occurrences in adx-core/docs/ and tests/README.md are documentation.

## Observations

**1. adx-core/apps/auth.** Build is separate: own Vite configuration and script, and application `dist` generates its own `remoteEntry.js` (adx-core/apps/auth/vite.config.ts:9-12). Both workflows publish the application separately, at its own bucket path and with its own CloudFront invalidation. This would support `separate`. But workflows build and copy `apps/auth`, absent from the snapshot (application is at `adx-core/apps/auth`), and install from a workspace excluding it. The artifact cannot be established to cover this application or be in use, so Deploy remains `Undetermined`. The deployment record stores `version: github.sha` per application (.github/workflows/deploy-microfrontends.yml:189-193). This is the entire repository commit rather than an application version. Manifest `version: 1.0.0` (adx-core/apps/auth/package.json:3) is unused in publication. Versioning `No`.

**2. adx-core/apps/file.** Same arrangement as auth, with path `apps/file` in workflows. Own build references exposes components absent from the snapshot (adx-core/apps/file/vite.config.ts:13-15). Workflow verification requires `index.html` in `dist` (.github/workflows/deploy-microfrontends.yml:129-132), and the folder has no `index.html` (see the structural review). Even with the path corrected, publication would fail at that step.

**3. adx-core/apps/module.** Same arrangement, but only `deploy-microfrontends.yml` covers `module` (.github/workflows/deploy-microfrontends.yml:45, 53). The `deploy-production.yml` matrix excludes it (.github/workflows/deploy-production.yml:213, 311). Rollback lists it among applications (scripts/deployment-rollback.sh:175). Own build depends on snapshot-missing files: exposes at adx-core/apps/module/vite.config.ts:15-17 and `./index.css` imported at adx-core/apps/module/src/main.tsx:4.

**4. adx-core/apps/shell.** Own build. Workflows publish it at environment root, `<ambiente>/` (.github/workflows/deploy-microfrontends.yml:153-155), and invalidate `/<ambiente>/*` (:174-178), including remote paths. The `deploy-production.yml` publishes it under `shell/`, like the others (:329). Both workflows disagree about shell location relative to remotes. The same `apps/shell` path discrepancy applies here. Even published, shell would load remotes from `localhost` (adx-core/apps/shell/vite.config.ts:11-18): the snapshot has no configuration connecting shell to published remote addresses. Only `package-workspace.json` has a `build:shell` (package-workspace.json:22), and it is unused. No independent version.

**5. adx-core/apps/tenant.** Same arrangement as auth, path `apps/tenant`. Expose `./TenantSwitcher` points to a missing file (adx-core/apps/tenant/vite.config.ts:13), and the folder lacks `index.html`, required by workflow verification (.github/workflows/deploy-microfrontends.yml:129-132).

**6. adx-core/apps/user.** Same as `file`: own build with missing exposes (adx-core/apps/user/vite.config.ts:13-15), without `index.html`, and workflows with path `apps/user`.

**7. adx-core/apps/workflow.** Same as `file`: own build with missing exposes (adx-core/apps/workflow/vite.config.ts:13-15), without `index.html`, and workflows with path `apps/workflow`.
