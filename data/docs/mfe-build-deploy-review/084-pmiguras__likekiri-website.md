# 084 — pmiguras/likekiri-website

## Repository overview

pnpm monorepo (pnpm-workspace.yaml:1-4) with two React/Vite shells (`apps/admin-shell`, `apps/web-shell`), ten federated remotes in `modules/*`, NestJS backend `apps/core` and libraries in `packages/*`. Root build only delegates to each member (package.json:9, `pnpm -r build`), and each application has its own `vite build`, with its own output: dashboard generates `dist` with `base: '/admin-assets/'` (apps/admin-shell/vite.config.ts:7); website generates a client bundle in `dist/client` and an SSR bundle in `dist/server` (apps/web-shell/vite.config.ts:10-27; apps/web-shell/package.json:8); each module generates its own `dist` with `remoteEntry.js` (e.g.: modules/hello/vite.config.ts:12, :24), and `clientes` also generates an SSR bundle in `dist-ssr` (modules/clientes/vite.config.ts:14; modules/clientes/package.json:8). No CI, application Dockerfile or cloud hosting configuration is present in the snapshot.

The publication described by the snapshot is production, on a private server with systemd and Caddy, without containers. Core runs in a systemd unit over checkout `/srv/likekiri/app` (infra/systemd/likekiri-core.service:12, :16), listens only on loopback (apps/core/src/main.ts:35; default port 3000 in apps/core/src/config.ts:5) and serves both shells: website static files at `/assets/` and dashboard files at `/admin-assets/` (apps/core/src/main.ts:21-32, with default directories `./apps/web-shell/dist` and `./apps/admin-shell/dist` in apps/core/src/config.ts:11-12), dashboard `index.html` (apps/core/src/shell/shell.service.ts:100-103) and website SSR, importing web-shell’s `server/entry-server.js` within the same process (apps/core/src/shell/shell.service.ts:81-87). Each module has its own systemd unit running its `server.mjs` from the module directory in the same checkout (e.g.: infra/systemd/likekiri-module-chat.service:10, :13), and this server serves module `dist` (e.g.: modules/hello/server.mjs:22, :98-113) on its own loopback port (e.g.: modules/hello/server.mjs:19). Caddy, whose file says blocks are manually added to the server Caddyfile (infra/caddy/likekiri.caddy:1-3), exposes `likekiri.com` and `admin.likekiri.com`, forwards each `/modules/<id>/*` to the module port and sends the rest to core (infra/caddy/likekiri.caddy:6-34, :47-78).

Thus each module is published in its own process and route, and both shells are released together in the core process. There is no deployment script in the snapshot: how checkout reaches `/srv/likekiri/app`, where build runs and which variables go into `EnvironmentFile` (for example each module’s public `MODULE_REMOTE_ENTRY`, modules/chat/server.mjs:36) remain outside the repository. Caddy also serves `/assets/*` from `/srv/likekiri/public` (infra/caddy/likekiri.caddy:9-13), a directory no snapshot artifact populates; see observation 2.

Artifacts without a frontend application: `infra/docker-compose.yml` is only development Postgres, as the file itself states (infra/docker-compose.yml:1-3, :5-6); `infra/ops/likekiri-ops` only performs git operations on the server repository (infra/ops/likekiri-ops:2-4, :14-59), called by module `ops` through sudo (infra/ops/sudoers.likekiri-ops:1); `infra/systemd/likekiri-core.service` publishes backend (and shells with it). The `ops-hosting` occurrence in modules/clientes/INTEGRACION-APPS.md:119 documents a `firebase deploy` of a Cloud Function from another application, which synchronizes customers with likekiri; it publishes no unit from this repository. The `cfg-public-path` occurrences are the `base` values of both shells (apps/admin-shell/vite.config.ts:7; apps/web-shell/vite.config.ts:10).

## Observations

**1. apps/admin-shell.** Own build (apps/admin-shell/package.json:9) generates a dashboard-only `dist`, with prefix `/admin-assets/` chosen to avoid collision with web-shell’s `/assets` in core (apps/admin-shell/vite.config.ts:6-7). No artifact publishes dashboard alone: core serves static files (apps/core/src/main.ts:27-32) and `index.html` (apps/core/src/shell/shell.service.ts:100-103) from `./apps/admin-shell/dist` (apps/core/src/config.ts:12), and Caddy for `admin.likekiri.com` forwards only requests outside `/modules/*` to core (infra/caddy/likekiri.caddy:76-78). Dashboard is therefore released in the same core process publishing web-shell (infra/systemd/likekiri-core.service:16): deploy `joint`. The `version` 0.1.0 (apps/admin-shell/package.json:3) is unused in publication.

**2. apps/web-shell.** Two own builds, client (`dist/client`, with fixed-name `islands.js`) and SSR (`dist/server`) (apps/web-shell/vite.config.ts:4-27; apps/web-shell/package.json:8). SSR bundle runs only inside core, which imports it by path (apps/core/src/shell/shell.service.ts:81-87), and core also serves `dist/client` at `/assets/` (apps/core/src/main.ts:21-26); website is released in the same process as dashboard and backend, deploy `joint`. Caddy for `likekiri.com` serves `/assets/*` directly from `/srv/likekiri/public` (infra/caddy/likekiri.caddy:9-13), indicating a copy of static files outside core, but nothing in the snapshot copies `dist/client` there, and page rendering still remains in core (infra/caddy/likekiri.caddy:32-34); this does not change the value. No versioning used in publication (apps/web-shell/package.json:3).

**3. modules/chat.** Own federated build, output `dist` (modules/chat/vite.config.ts:10, :18). Deploy `separate`: own systemd unit runs `server.mjs` in module directory (infra/systemd/likekiri-module-chat.service:10, :13), serving `dist` (modules/chat/server.mjs:37) at `127.0.0.1:4009` (modules/chat/server.mjs:34), and own route in both domains, because the module enters website (widget) and dashboard (infra/caddy/likekiri.caddy:28-30, :69-71). Process, `EnvironmentFile` (infra/systemd/likekiri-module-chat.service:11) and port belong to the module; checkout `/srv/likekiri/app` is the same for all units. Manifest publishes `version: pkg.version` (modules/chat/server.mjs:490), but core only records it in logs and registry listing (apps/core/src/registry/registry.service.ts:155, :337); it is not a version used to publish or release the module, and all modules are at 0.1.0 (modules/chat/package.json:3): `No`.
