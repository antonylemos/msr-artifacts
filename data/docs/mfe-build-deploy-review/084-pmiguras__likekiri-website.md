# 084 — pmiguras/likekiri-website

## Leitura do repositório

Monorepo pnpm (pnpm-workspace.yaml:1-4) com dois shells React/Vite (`apps/admin-shell`, `apps/web-shell`), dez remotes federados em `modules/*`, o backend NestJS `apps/core` e bibliotecas em `packages/*`. O build da raiz só delega a cada membro (package.json:9, `pnpm -r build`), e cada aplicação tem o seu `vite build`, com saída própria: o painel gera `dist` com `base: '/admin-assets/'` (apps/admin-shell/vite.config.ts:7); o site gera um bundle cliente em `dist/client` e um bundle SSR em `dist/server` (apps/web-shell/vite.config.ts:10-27; apps/web-shell/package.json:8); cada módulo gera o seu `dist` com `remoteEntry.js` (ex.: modules/hello/vite.config.ts:12, :24), e `clientes` gera também um bundle SSR em `dist-ssr` (modules/clientes/vite.config.ts:14; modules/clientes/package.json:8). Não há CI, Dockerfile de aplicação nem configuração de hospedagem em nuvem no snapshot.

A publicação descrita pelo snapshot é de produção, num servidor próprio com systemd e Caddy, sem contêineres. O core roda numa unidade systemd sobre o checkout `/srv/likekiri/app` (infra/systemd/likekiri-core.service:12, :16), escuta só em loopback (apps/core/src/main.ts:35; porta padrão 3000 em apps/core/src/config.ts:5) e serve os dois shells: os estáticos do site em `/assets/` e os do painel em `/admin-assets/` (apps/core/src/main.ts:21-32, com os diretórios padrão `./apps/web-shell/dist` e `./apps/admin-shell/dist` em apps/core/src/config.ts:11-12), o `index.html` do painel (apps/core/src/shell/shell.service.ts:100-103) e o SSR do site, importando `server/entry-server.js` do web-shell no próprio processo (apps/core/src/shell/shell.service.ts:81-87). Cada módulo tem uma unidade systemd própria que roda o seu `server.mjs` a partir do diretório do módulo no mesmo checkout (ex.: infra/systemd/likekiri-module-chat.service:10, :13), e esse servidor serve o `dist` do módulo (ex.: modules/hello/server.mjs:22, :98-113) numa porta de loopback própria (ex.: modules/hello/server.mjs:19). O Caddy, cujo arquivo diz que os blocos são acrescentados à mão ao Caddyfile do servidor (infra/caddy/likekiri.caddy:1-3), expõe `likekiri.com` e `admin.likekiri.com`, encaminha cada `/modules/<id>/*` para a porta do módulo e manda o resto para o core (infra/caddy/likekiri.caddy:6-34, :47-78).

Assim, os módulos são publicados cada um em processo e rota próprios, e os dois shells saem juntos no processo do core. Não há script de deploy no snapshot: como o checkout chega a `/srv/likekiri/app`, onde o build roda e quais variáveis vão nos `EnvironmentFile` (por exemplo, o `MODULE_REMOTE_ENTRY` público de cada módulo, modules/chat/server.mjs:36) fica fora do repositório. O Caddy também serve `/assets/*` de `/srv/likekiri/public` (infra/caddy/likekiri.caddy:9-13), diretório que nenhum artefato do snapshot preenche; ver a observação 2.

Artefatos sem aplicação frontend: `infra/docker-compose.yml` é só o Postgres de desenvolvimento, como o próprio arquivo diz (infra/docker-compose.yml:1-3, :5-6); `infra/ops/likekiri-ops` faz só operações git no repositório do servidor (infra/ops/likekiri-ops:2-4, :14-59), chamado pelo módulo `ops` via sudo (infra/ops/sudoers.likekiri-ops:1); `infra/systemd/likekiri-core.service` publica o backend (e, com ele, os shells). A ocorrência `ops-hosting` em modules/clientes/INTEGRACION-APPS.md:119 é documentação de um `firebase deploy` de uma Cloud Function de outra aplicação, que sincroniza clientes com o likekiri; não publica nenhuma unidade deste repositório. As ocorrências `cfg-public-path` são os `base` dos dois shells (apps/admin-shell/vite.config.ts:7; apps/web-shell/vite.config.ts:10).

## Observações

**1. apps/admin-shell.** O build é próprio (apps/admin-shell/package.json:9) e gera um `dist` só do painel, com prefixo `/admin-assets/` escolhido para não colidir com os `/assets` do web-shell no core (apps/admin-shell/vite.config.ts:6-7). Não há artefato que publique o painel sozinho: o core serve os estáticos (apps/core/src/main.ts:27-32) e o `index.html` (apps/core/src/shell/shell.service.ts:100-103) a partir de `./apps/admin-shell/dist` (apps/core/src/config.ts:12), e o Caddy de `admin.likekiri.com` só encaminha ao core o que não é `/modules/*` (infra/caddy/likekiri.caddy:76-78). O painel sai, portanto, no mesmo processo do core que publica o web-shell (infra/systemd/likekiri-core.service:16): deploy `conjunto`. O `version` 0.1.0 (apps/admin-shell/package.json:3) não é usado em publicação.

**2. apps/web-shell.** Dois builds próprios, cliente (`dist/client`, com `islands.js` de nome fixo) e SSR (`dist/server`) (apps/web-shell/vite.config.ts:4-27; apps/web-shell/package.json:8). O bundle SSR só roda dentro do core, que o importa por caminho (apps/core/src/shell/shell.service.ts:81-87), e o core também serve `dist/client` em `/assets/` (apps/core/src/main.ts:21-26); o site sai no mesmo processo que o painel e o backend, deploy `conjunto`. O Caddy de `likekiri.com` serve `/assets/*` direto de `/srv/likekiri/public` (infra/caddy/likekiri.caddy:9-13), o que indica uma cópia dos estáticos fora do core, mas nada no snapshot copia o `dist/client` para lá, e mesmo assim o render das páginas continua no core (infra/caddy/likekiri.caddy:32-34); isso não muda o valor. Sem versionamento usado em publicação (apps/web-shell/package.json:3).

**3. modules/chat.** Build federado próprio, saída `dist` (modules/chat/vite.config.ts:10, :18). Deploy `separado`: unidade systemd própria que roda `server.mjs` no diretório do módulo (infra/systemd/likekiri-module-chat.service:10, :13), servindo o `dist` (modules/chat/server.mjs:37) em `127.0.0.1:4009` (modules/chat/server.mjs:34), e rota própria nos dois domínios, porque o módulo entra no site (widget) e no painel (infra/caddy/likekiri.caddy:28-30, :69-71). O processo, o `EnvironmentFile` (infra/systemd/likekiri-module-chat.service:11) e a porta são do módulo; o checkout `/srv/likekiri/app` é o mesmo de todas as unidades. O manifesto publica `version: pkg.version` (modules/chat/server.mjs:490), mas o core só o registra em log e na listagem do registro (apps/core/src/registry/registry.service.ts:155, :337); não é versão usada para publicar ou liberar o módulo, e todos os módulos estão em 0.1.0 (modules/chat/package.json:3): `No`. Isso vale para todos os módulos abaixo.
