# 270 — shreyash1086/mfe

## Repository overview

Eleven React applications with Webpack 5, without workspace: each directory has its own `package.json` with `build` = `webpack --mode production` (e.g.: module-cloud-labs/package.json:6) and `webpack.config.js`, and no root manifest exists. No CI is present in snapshot. The only packaging and publication path is docker-compose.yml, starting twelve services on a shared network (docker-compose.yml:181-184): an nginx gateway and eleven images, one per application.

Each application has its own multi-stage Dockerfile. Stage `builder` installs application dependencies and runs its build; second stage copies only that application’s `dist/` to `nginx:alpine` with application’s own `nginx.conf` (module-cloud-labs/Dockerfile:2-22; shared-design-system/Dockerfile:2-25; shell-app/Dockerfile:2-33). All nine modules and shell use root context (e.g.: docker-compose.yml:42-44) because they copy `shared-design-system` to `/shared-design-system` before installing (module-cloud-labs/Dockerfile:6-7; shell-app/Dockerfile:6-7): destination of dependency `file:../shared-design-system` (module-cloud-labs/package.json:15) and where each application’s Tailwind reads design system tokens (module-cloud-labs/tailwind.config.js:1). No module or shell `.js`/`.jsx` file imports package `shared-design-system` by name; design system code arrives at runtime through remote `sharedDesignSystem` (composition review). All nine module `nginx.conf` files, shell file and design system file use same configuration (differing only in comments): open CORS, SPA fallback, long caching for static files and uncached `remoteEntry.js` (module-cloud-labs/nginx.conf:10-12, 16-18, 21-25, 30-34). Root `.dockerignore` excludes `node_modules`, `dist`, `docs` and compose itself from context (.dockerignore:2-9, 17-19); `.dockerignore` files within each directory apply only to design system, the only service whose context is its own directory (docker-compose.yml:30-32).

Gateway is service `nginx`, image `nginx:alpine` without build, with mounted nginx/nginx.conf and published port 80 (docker-compose.yml:5-11). It packages no application: only forwards. The `/` goes to shell container (nginx/nginx.conf:18-19), and each `/<nome>-remote/remoteEntry.js` and static files under same prefix go to corresponding application container, removing prefix (e.g.: nginx/nginx.conf:37-46). This routing table connects relative URLs in shell `index.html` (shell-app/public/index.html:24-33) to containers; all `webpack.config.js` files use `publicPath: "auto"` (e.g.: module-cloud-labs/webpack.config.js:10; shell-app/webpack.prod.config.js:22), allowing each remote’s chunks to be requested under prefix from which `remoteEntry.js` came. The `ops-cors` occurrences in `webpack.config.js` files are `devServer` headers (e.g.: module-cloud-labs/webpack.config.js:76-78); shell occurrences also include development proxy to two AWS Lambda URLs (shell-app/webpack.config.js:70-91), external backend rather than frontend application. The `shell-app/src/config/amplify-config.js` configures Cognito authentication, not hosting.

Compose `depends_on` only orders startup: modules wait for design system and shell waits for all (docker-compose.yml:50-51, 168-178). The only build dependency between applications is in shell: its Dockerfile copies source of all nine modules for Tailwind to generate classes they use (shell-app/Dockerfile:13-22; shell-app/tailwind.config.js:4-17). Shell artifact contains CSS for these classes, not module code. Shell also has two configurations: script `build` uses `webpack.config.js` (shell-app/package.json:6), while image uses `webpack.prod.config.js` (shell-app/Dockerfile:26), with bundle named by `contenthash` (shell-app/webpack.prod.config.js:21). No application has its own version used in publication: all declare `"version": "1.0.0"` (e.g.: module-cloud-labs/package.json:3), unused by any artifact. Documentation describes modules "each running in its own Docker container" (README.md:4) and an "independently deployable" platform (docs/ARCHITECTURE.md:3); this does not decide table, but matches compose. README still describes three modules and four containers (README.md:4, 39), while compose has nine modules.

## Observations

**1. module-assessment.** Separate build: Dockerfile runs module’s own `build` (module-assessment/package.json:6; module-assessment/Dockerfile:14-15), and generated `dist/` contains only its code; design system arrives at runtime through federated remote. Separate deploy: second stage puts this `dist/` in module-only nginx image (module-assessment/Dockerfile:18-20), its own compose service, container `mfe-assessment` (docker-compose.yml:145-156). Gateway serves `/assessment-remote/remoteEntry.js` and prefix static files from this container (nginx/nginx.conf:133-140). What module shares with others concerns build: design system copy in context (module-assessment/Dockerfile:6-7) and same root context. Its `.dockerignore` and `nginx.conf` differ from others only in form (module-assessment/.dockerignore:1-6; module-assessment/nginx.conf:7-30), and first is not read because context is root (docker-compose.yml:147-148). No own version: `"version": "1.0.0"` (module-assessment/package.json:3) is unused in publication.

**2. module-cloud-console.** Same arrangement as module 1: module’s own build (module-cloud-console/Dockerfile:14-15), own nginx image (module-cloud-console/Dockerfile:18-20), service `cloud-console` (docker-compose.yml:80-91) and routes `/cloud-console-remote/` in gateway (nginx/nginx.conf:73-80). No own version.

**3. module-cloud-labs.** Same arrangement as module 1: module-cloud-labs/Dockerfile:14-15 and :18-20, service `cloud-labs` (docker-compose.yml:41-52), routes `/cloud-labs-remote/` (nginx/nginx.conf:37-44). No own version.

**4. module-code-environment.** Same arrangement as module 1: module-code-environment/Dockerfile:14-15 and :18-20, service `code-environment` (docker-compose.yml:106-117), routes `/code-environment-remote/` (nginx/nginx.conf:97-104). No own version.

**5. module-code-module.** Same arrangement as module 1: module-code-module/Dockerfile:14-15 and :18-20, service `code-module` (docker-compose.yml:119-130), routes `/code-module-remote/` (nginx/nginx.conf:109-116). No own version.

**6. module-content-uploading.** Same arrangement as module 1: module-content-uploading/Dockerfile:14-15 and :18-20, service `content-uploading` (docker-compose.yml:132-143), routes `/content-uploading-remote/` (nginx/nginx.conf:121-128). The `nginx.conf` differs from standard only in comments, like module 1’s (module-content-uploading/nginx.conf:7-30). No own version.

**7. module-dashboard.** Same arrangement as module 1: module-dashboard/Dockerfile:14-15 and :18-20, service `dashboard` (docker-compose.yml:54-65), routes `/dashboard-remote/` (nginx/nginx.conf:49-56). No own version.

**8. module-logging.** Same arrangement as module 1: module-logging/Dockerfile:14-15 and :18-20, service `logging` (docker-compose.yml:93-104), routes `/logging-remote/` (nginx/nginx.conf:85-92). Gateway prefix follows module name rather than shell route `/system-logs` (composition review). No own version.

**9. module-virtual-machine.** Same arrangement as module 1: module-virtual-machine/Dockerfile:14-15 and :18-20, service `virtual-machine` (docker-compose.yml:67-78), routes `/virtual-machine-remote/` (nginx/nginx.conf:61-68). No own version.

**10. shared-design-system.** Separate build: Dockerfile installs and runs `build` from own directory (shared-design-system/Dockerfile:7-12). The only application built with its own directory as context (docker-compose.yml:30-32), hence only one whose `.dockerignore` applies (shared-design-system/.dockerignore:1-6). Separate deploy: own nginx image (shared-design-system/Dockerfile:15-21), service `shared-design-system` (docker-compose.yml:29-38), routes `/design-system-remote/` in gateway (nginx/nginx.conf:25-32). Other ten services declare `depends_on` on it (e.g.: docker-compose.yml:50-51), but this only orders startup. Its source also enters build of other ten images (e.g.: module-cloud-labs/Dockerfile:6-7), for `file:` dependency and Tailwind tokens; design system served at runtime is only this container’s `remoteEntry.js`. No own version (shared-design-system/package.json:3).

**11. shell-app.** Separate build, but least isolated in source: image uses `webpack.prod.config.js` (shell-app/Dockerfile:26), not script `build` (shell-app/package.json:6), and copies source of all nine modules and design system for Tailwind (shell-app/Dockerfile:6-7, 13-22; shell-app/tailwind.config.js:4-17). Thus shell CSS depends on classes used in modules, and a new module class receives shell styling only when shell is rebuilt. Module code does not enter bundle: modules load at runtime (composition review). Separate deploy: own nginx image (shell-app/Dockerfile:29-31) and service `shell` (docker-compose.yml:159-179), served by gateway at `/` (nginx/nginx.conf:18-22). Remote URLs are not injected at deploy: fixed in shell `index.html`, selected by browser port (shell-app/public/index.html:18-47), so changing remote address requires rebuilding shell. No own version (shell-app/package.json:3).
