# 270 — shreyash1086/mfe

## Leitura do repositório

Onze aplicações React com Webpack 5, sem workspace: cada diretório tem seu `package.json` com `build` = `webpack --mode production` (ex.: module-cloud-labs/package.json:6) e seu `webpack.config.js`, e não há manifesto na raiz. Não há CI no snapshot. O único caminho de empacotamento e publicação é o docker-compose.yml, que sobe doze serviços numa rede comum (docker-compose.yml:181-184): um gateway nginx e onze imagens, uma por aplicação.

Cada aplicação tem um Dockerfile multi-estágio próprio. O estágio `builder` instala as dependências da aplicação e roda o build dela; o segundo estágio copia só o `dist/` dessa aplicação para um `nginx:alpine` com o `nginx.conf` da própria aplicação (module-cloud-labs/Dockerfile:2-22; shared-design-system/Dockerfile:2-25; shell-app/Dockerfile:2-33). Os nove módulos e o shell usam a raiz como contexto (ex.: docker-compose.yml:42-44) porque copiam o `shared-design-system` para `/shared-design-system` antes de instalar (module-cloud-labs/Dockerfile:6-7; shell-app/Dockerfile:6-7): é o destino da dependência `file:../shared-design-system` (module-cloud-labs/package.json:15) e de onde o Tailwind de cada aplicação lê os tokens do design system (module-cloud-labs/tailwind.config.js:1). Nenhum arquivo `.js`/`.jsx` de módulo ou do shell importa o pacote `shared-design-system` pelo nome; o código do design system chega em runtime pelo remote `sharedDesignSystem` (revisão de composição). Os nove `nginx.conf` dos módulos, o do shell e o do design system são a mesma configuração (diferem só nos comentários): CORS aberto, fallback de SPA, cache longo para estáticos e `remoteEntry.js` sem cache (module-cloud-labs/nginx.conf:10-12, 16-18, 21-25, 30-34). O `.dockerignore` da raiz exclui `node_modules`, `dist`, `docs` e o próprio compose do contexto (.dockerignore:2-9, 17-19); os `.dockerignore` dentro de cada diretório só valem para o design system, o único serviço cujo contexto é o próprio diretório (docker-compose.yml:30-32).

O gateway é o serviço `nginx`, imagem `nginx:alpine` sem build, com o nginx/nginx.conf montado e a porta 80 publicada (docker-compose.yml:5-11). Ele não empacota aplicação: só encaminha. `/` vai ao contêiner do shell (nginx/nginx.conf:18-19), e cada `/<nome>-remote/remoteEntry.js` e os estáticos do mesmo prefixo vão ao contêiner da aplicação correspondente, com o prefixo removido (ex.: nginx/nginx.conf:37-46). É essa tabela de rotas que liga as URLs relativas do `index.html` do shell (shell-app/public/index.html:24-33) aos contêineres; todos os `webpack.config.js` usam `publicPath: "auto"` (ex.: module-cloud-labs/webpack.config.js:10; shell-app/webpack.prod.config.js:22), o que deixa os chunks de cada remote serem pedidos sob o prefixo de onde veio o `remoteEntry.js`. As ocorrências `ops-cors` dos `webpack.config.js` são cabeçalhos do `devServer` (ex.: module-cloud-labs/webpack.config.js:76-78); as do shell incluem também o proxy de desenvolvimento para duas URLs Lambda da AWS (shell-app/webpack.config.js:70-91), que são backend externo, não aplicação frontend. O `shell-app/src/config/amplify-config.js` configura autenticação Cognito, não hospedagem.

O `depends_on` do compose só ordena a partida: os módulos esperam o design system e o shell espera todos (docker-compose.yml:50-51, 168-178). A única dependência de build entre aplicações está no shell: o Dockerfile dele copia as fontes dos nove módulos para o Tailwind gerar as classes que eles usam (shell-app/Dockerfile:13-22; shell-app/tailwind.config.js:4-17). O que sai no artefato do shell é o CSS dessas classes, não o código dos módulos. O shell também tem dois configs: o script `build` usa o `webpack.config.js` (shell-app/package.json:6), e a imagem usa o `webpack.prod.config.js` (shell-app/Dockerfile:26), com bundle de nome por `contenthash` (shell-app/webpack.prod.config.js:21). Nenhuma aplicação tem versão própria usada na publicação: todas declaram `"version": "1.0.0"` (ex.: module-cloud-labs/package.json:3), sem uso por nenhum artefato. A documentação descreve módulos "each running in its own Docker container" (README.md:4) e uma plataforma "independently deployable" (docs/ARCHITECTURE.md:3); isso não decide a tabela, mas confere com o compose. O README ainda fala em três módulos e quatro contêineres (README.md:4, 39), e o compose tem nove módulos.

## Observações

**1. module-assessment.** Build separado: o Dockerfile roda o `build` do próprio módulo (module-assessment/package.json:6; module-assessment/Dockerfile:14-15), e o `dist/` gerado só contém o código dele; o design system chega em runtime pelo remote federado. Deploy separado: o segundo estágio põe esse `dist/` numa imagem nginx só do módulo (module-assessment/Dockerfile:18-20), que é um serviço próprio do compose, contêiner `mfe-assessment` (docker-compose.yml:145-156). O gateway serve `/assessment-remote/remoteEntry.js` e os estáticos do prefixo a partir desse contêiner (nginx/nginx.conf:133-140). O que o módulo compartilha com os outros está no build: a cópia do design system no contexto (module-assessment/Dockerfile:6-7) e o mesmo contexto de raiz. O `.dockerignore` e o `nginx.conf` dele diferem dos demais só na forma (module-assessment/.dockerignore:1-6; module-assessment/nginx.conf:7-30), e o primeiro não é lido, porque o contexto é a raiz (docker-compose.yml:147-148). Sem versão própria: `"version": "1.0.0"` (module-assessment/package.json:3) não é usado na publicação.

**2. module-cloud-console.** Mesmo arranjo do módulo 1: build do próprio módulo (module-cloud-console/Dockerfile:14-15), imagem nginx própria (module-cloud-console/Dockerfile:18-20), serviço `cloud-console` (docker-compose.yml:80-91) e rotas `/cloud-console-remote/` no gateway (nginx/nginx.conf:73-80). Sem versão própria.

**9. module-virtual-machine.** Mesmo arranjo do módulo 1: module-virtual-machine/Dockerfile:14-15 e :18-20, serviço `virtual-machine` (docker-compose.yml:67-78), rotas `/virtual-machine-remote/` (nginx/nginx.conf:61-68). Sem versão própria.

**10. shared-design-system.** Build separado: o Dockerfile instala e roda o `build` do próprio diretório (shared-design-system/Dockerfile:7-12). É a única aplicação construída com o próprio diretório como contexto (docker-compose.yml:30-32), e por isso a única cujo `.dockerignore` vale (shared-design-system/.dockerignore:1-6). Deploy separado: imagem nginx própria (shared-design-system/Dockerfile:15-21), serviço `shared-design-system` (docker-compose.yml:29-38), rotas `/design-system-remote/` no gateway (nginx/nginx.conf:25-32). Os outros dez serviços declaram `depends_on` nele (ex.: docker-compose.yml:50-51), mas isso só ordena a partida. As fontes dele também entram no build das outras dez imagens (ex.: module-cloud-labs/Dockerfile:6-7), para a dependência `file:` e os tokens do Tailwind; o que é servido como design system em runtime é só o `remoteEntry.js` deste contêiner. Sem versão própria (shared-design-system/package.json:3).

**11. shell-app.** Build separado, mas o menos isolado nas fontes: a imagem usa o `webpack.prod.config.js` (shell-app/Dockerfile:26), não o script `build` (shell-app/package.json:6), e copia as fontes dos nove módulos e do design system para o Tailwind (shell-app/Dockerfile:6-7, 13-22; shell-app/tailwind.config.js:4-17). Assim, o CSS do shell depende das classes usadas nos módulos, e uma classe nova num módulo só ganha estilo do shell quando o shell é reconstruído. O código dos módulos não entra no bundle: eles são carregados em runtime (revisão de composição). Deploy separado: imagem nginx própria (shell-app/Dockerfile:29-31) e serviço `shell` (docker-compose.yml:159-179), que o gateway serve em `/` (nginx/nginx.conf:18-22). As URLs dos remotes não são injetadas no deploy: estão fixas no `index.html` do shell, escolhidas pela porta do navegador (shell-app/public/index.html:18-47), e por isso mudar um endereço de remote exige reconstruir o shell. Sem versão própria (shell-app/package.json:3).
