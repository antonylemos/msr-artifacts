# 272 — scality/metalk8s

## Repository overview

MetalK8s is a production Kubernetes distribution, and frontend is a small part of a much larger build. No workspace: `shell-ui` and `ui` each have their own `package.json`, `package-lock.json` and `rspack.config.ts`, and both `build` scripts run `tsc --noEmit` and `rspack build` in application directory (shell-ui/package.json:9; ui/package.json:39). Product build is Python buildchain (doit): job `build` in `.github/workflows/build.yaml` runs `./doit.sh` and stores ISO `_build/metalk8s.iso` and `product.txt` (.github/workflows/build.yaml:86-95). Node builds run within a builder image generated from `ui/Dockerfile`, only installing dependencies and calling `ui/entrypoint.sh` (ui/Dockerfile:9-19; ui/entrypoint.sh:5-8); same Dockerfile serves both applications with different contexts (`UI_BUILDER` and `SHELL_UI_BUILDER`, buildchain/buildchain/builder.py:94-115). Tasks `ui` and `shell_ui` mount each application’s source in this builder and write results to separate build root directories (buildchain/buildchain/ui.py:115-128; buildchain/buildchain/shell_ui.py:64-79).

Images go inside ISO (buildchain/buildchain/image.py:3-10). Two concern frontend. Image `shell-ui` is built from shell’s own Dockerfile (buildchain/buildchain/image.py:417-421): a Node stage runs `npm run rsbuild`, and nginx serves result at `/shell` (shell-ui/Dockerfile:4-27), with fallback to `/shell/index.html` (shell-ui/conf/nginx.conf:23-28). Image `metalk8s-ui` is assembled from buildchain builds (`task_dep=["ui", "shell_ui", "doc"]`, buildchain/buildchain/image.py:422-437) and copies `ui` build at root, documentation at `/docs` and shell build at `/shell` into same nginx (images/metalk8s-ui/Dockerfile:9-11). This image’s nginx uses `/shell/index.html` as index and serves, through `alias`, ConfigMap-generated configurations for UI and shell, including `/shell/deployed-ui-apps.json` (images/metalk8s-ui/conf/nginx.conf:23-57). Both images receive product version (buildchain/buildchain/versions.py:257-266).

Deploy uses Salt states creating Scality UI operator resources (`ui.scality.com/v1alpha1`), whose own deploy is at salt/metalk8s/addons/ui-operator/deployed/manifests.sls:40. Shell becomes two `ScalityUI` resources (`shell-ui-cp` and `shell-ui-wp`) with image `shell-ui` (salt/metalk8s/addons/shell-ui/deployed/ui-operator-cr.sls:3, :15-32, :77-94). The `ui` becomes a `ScalityUIComponent` `metalk8s-ui` with image `metalk8s-ui` and `mountPath: /usr/share/nginx/html/.well-known`, linked to `shell-ui-cp` by a `ScalityUIComponentExposer` (salt/metalk8s/addons/ui/deployed/ui-operator-cr.sls:3, :15-25, :52-63). All three addons enter state `metalk8s.deployed` together (salt/metalk8s/deployed/init.sls:10-12). Same addon `ui` creates Ingress resources for API proxies and documentation, the latter pointing to service `metalk8s-ui` (salt/metalk8s/addons/ui/deployed/ingress.sls:16-126). Old `Deployment` `metalk8s-ui` appears only as a template (salt/metalk8s/addons/ui/deployed/files/metalk8s-ui-deployment.yaml.j2:2-38), referenced only in formula test configuration (salt/tests/unit/formulas/config.yaml:181); post-install removes legacy volumes and ConfigMaps from earlier installation (salt/metalk8s/addons/ui/deployed/ui-operator-post-install.sls:1-60).

In CI, shell has its own path beyond ISO. The `build-shell-ui.yaml` builds shell image with `working-directory: shell-ui`, extracts directory `shell` into `shell.tar`, generates SBOM and sends everything to artifact server (.github/workflows/build-shell-ui.yaml:27-78); called by `build.yaml` and `pre-merge.yaml` (.github/workflows/build.yaml:113-117; .github/workflows/pre-merge.yaml:113-117). The `publish.yaml` has only job `publish-shell-ui`: retags image and sends it to `ghcr.io/<repositório>/shell-ui`, and in production attaches `shell.tar` to a GitHub release named `Metalk8s <versão>` (.github/workflows/publish.yaml:29-160). It runs after every merge and on promotion (.github/workflows/post-merge.yaml:9-20; .github/workflows/promote.yaml:41-48). The `ui` has no own CI job or image: released only through ISO. Version used always belongs to product, read from `VERSION` or `product.txt` (.github/workflows/build-shell-ui.yaml:27-30; .github/workflows/publish.yaml:71-76; VERSION:1-4); `SHELL_UI_VERSION` read by buildchain from shell `package.json` is unused elsewhere (buildchain/buildchain/versions.py:63-67).

Other `ops-*` and `ci-*` occurrences in `matches.csv` cover no frontend application. They are Dockerfiles of product images (`images/metalk8s-alert-logger`, `metalk8s-boot-cache`, `metalk8s-keepalived`, `metalk8s-utils`, `salt-master`), Go operators (operator/Dockerfile:1-3; `storage-operator/Dockerfile`) and their manifests (operator/deploy/manifests.yaml:850-858; `storage-operator/deploy/manifests.yaml`), documentation, package and tool builders (docs/Dockerfile:1-6; `packages/redhat/8` and `9`; tools/lib-alert-tree/Dockerfile:1-2; `tools/get-kubeadm-manifests`; patches in `tools/upgrade-operator-sdk`), static registry and its test compose (buildchain/static-container-registry/docker-compose.test.yml:1-3), and third-party charts vendored in `charts/` (cert-manager, dex, fluent-bit, ingress-nginx, kube-prometheus-stack, loki, node-problem-detector, prometheus-adapter, thanos), whose `ops-compose-service` and `ops-hosting` occurrences are `Chart.yaml` fields and README excerpts (e.g.: charts/thanos/Chart.yaml:26). The `ops-hosting` occurrences in `CHANGELOG.md`, operator READMEs and images/metalk8s-utils/Dockerfile:86 also do not concern frontend, and `docs/developer/deploy/*.rst` documents deploying a new MetalK8s image (docs/developer/deploy/index.rst:1-2). Other workflows (devcontainer, docs, changelog, CodeQL, crons, single-node, multinode, upgrade and downgrade tests, e2e, SBOM, lifecycle, release, renovate, review) do not build or publish `shell-ui` or `ui` separately; `single-node-test.yaml` only collects `ui` Cypress videos (.github/workflows/single-node-test.yaml:253). The `ops-cors` occurrence is `ui` dev server CORS header (ui/rspack.config.ts:22-26, :208-211).

## Observations

**1. shell-ui.** Separate build: shell rspack generates its own directory, and buildchain performs it in builder with context `shell-ui` (buildchain/buildchain/builder.py:105-115; buildchain/buildchain/shell_ui.py:43-61), while own image repeats same build in Node stage (shell-ui/Dockerfile:20). Deploy has two forms in snapshot, hence `Undetermined`. First, shell is published separately: image `shell-ui` containing only shell (shell-ui/Dockerfile:24-28), carried in ISO (buildchain/buildchain/image.py:417-421), used by both `ScalityUI` resources (salt/metalk8s/addons/shell-ui/deployed/ui-operator-cr.sls:32, :94) and published in CI to `ghcr.io` and GitHub release (.github/workflows/publish.yaml:106-160). Second, shell build is copied to `/shell` in image `metalk8s-ui`, alongside `ui` and documentation (images/metalk8s-ui/Dockerfile:9-11), and this image’s nginx has `/shell/index.html` as index and serves shell configuration (images/metalk8s-ui/conf/nginx.conf:24-27, :44-51). This image belongs to `ScalityUIComponent` of `ui`, mounted with `mountPath` at `.well-known` (salt/metalk8s/addons/ui/deployed/ui-operator-cr.sls:24-25); operator serving it is absent from snapshot, so whether its `/shell` is still accessed cannot be known. Versioning `No`: image and release use product version, same for all images (.github/workflows/build-shell-ui.yaml:27-32; .github/workflows/publish.yaml:71-76; buildchain/buildchain/versions.py:262-266), and `version` of `package.json` (`1.0.0`, shell-ui/package.json:3) is read in buildchain/buildchain/versions.py:63-67 without publication use.

**2. ui.** Separate build: rspack of `ui` generates `build/` with `publicPath: '/metalk8s/'` (ui/rspack.config.ts:37-43), performed by buildchain in builder of `ui/Dockerfile`, with mounted source and output at `UI_BUILD_ROOT` (buildchain/buildchain/ui.py:48-64, :115-128). Result belongs only to it; bundle entry is an empty file and UI outputs as remote (structural review), not changing build. Joint deploy: the only artifact packaging `ui` is image `metalk8s-ui`, carrying documentation and shell build in same nginx image (images/metalk8s-ui/Dockerfile:9-11; buildchain/buildchain/image.py:422-437). Own `ScalityUIComponent` and `ScalityUIComponentExposer` (salt/metalk8s/addons/ui/deployed/ui-operator-cr.sls:15-25, :52-63) use this image, so do not publish it separately. The `ui` has no CI job or image on `ghcr.io`: reaches cluster only through ISO. Versioning `No`: product version, read from `VERSION` (ui/rspack.config.ts:13-20), enters remoteEntry name (composition review, ui/rspack.config.ts:120) and image `metalk8s-ui` tag (buildchain/buildchain/versions.py:257-261), and `version` `0.1.0` of `package.json` (ui/package.json:3) is unused in publication.
