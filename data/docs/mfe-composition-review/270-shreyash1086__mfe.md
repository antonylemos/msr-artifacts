# 270 — shreyash1086/mfe

## Repository overview

A laboratory and assessment platform in React with Webpack 5 Module Federation, Docker and nginx. `shell-app` is the host: it loads nine `module-*` remotes at runtime, one per route (shell-app/src/App.jsx:167-277), and wraps them with its own authentication and theme (shell-app/src/App.jsx:290-297). `shared-design-system` plays a third role: a federated remote (`name: "sharedDesignSystem"`, shared-design-system/webpack.config.js:36-49) consumed by the shell and all nine modules, which receive its `ThemeProvider`, global CSS and components such as `PageHeader` and `Card`. Modules do not load one another. The README still describes only three modules (README.md:4, 9-17), but the snapshot has nine, all connected to the shell.

Both loading chains use the same federation in different ways. For the nine modules, the shell declares no `remotes` in webpack (comment in shell-app/webpack.config.js:32-33): a custom loader injects `remoteEntry.js` through `<script>`, initializes the shared scope and requests the exposed module from the container (shell-app/src/remotes/remoteLoader.js:4-65), with the URL read from `window.__RUNTIME_REMOTE_CONFIG__` (shell-app/src/config/remoteConfig.js:21-31). That object is assembled in the shell's `index.html`: relative paths behind the gateway when the port is 80/443 or empty, `localhost:3001`–`3010` in development (shell-app/public/index.html:18-51). In Docker, the gateway (nginx/nginx.conf:18-134) forwards each `/<nome>-remote/remoteEntry.js` to the service container in docker-compose.yml. English explanation of the path placeholder: name. For the design system, the shell and each module declare remote `sharedDesignSystem` as a `promise`, which first reuses `window.sharedDesignSystem` and only injects the script if it does not exist (e.g.: module-assessment/webpack.config.js:39-50, :41). When a module runs inside the shell, it reuses the container already loaded by the shell.

Beyond module loading, the units exchange two kinds of state. The shell's `AuthProvider` publishes bridge `window.__SHELL_AUTH__` (shell-app/src/contexts/AuthContext.jsx:228-262), with getters, `onAuthChange` and `signOut`, and notifies subscribers on login and logout (shell-app/src/contexts/AuthContext.jsx:45, 137, 219); all nine modules subscribe to the bridge when they find it and otherwise use Amplify independently (e.g.: module-dashboard/src/AuthContext.jsx:111-145). Theme passes through the `theme` key in `localStorage` and the `dark` class of `documentElement`, written by the exposed `ThemeProvider` (shared-design-system/src/contexts/ThemeContext.jsx:14-22) in each instance: the shell's and each module's. Because the same shell–module pair exchanges both states, and INSTRUCTIONS combine the same Source, Target and Type trio in one row, each pair has a single `communication` row with both pieces of evidence and mechanism `events`, according to the decision recorded at the end.

What did not become a relationship: both `<iframe>` elements show an external Guacamole client with a VM screen, not a frontend unit (source code review, module-assessment/src/pages/KodeEnvSection.jsx:369 and module-code-module/src/CodeModule.jsx:847, both `No`). Modules' `signOut` forwards to the bridge's (e.g.: module-dashboard/src/AuthContext.jsx:148-151), but no module calls it: module-content-uploading/src/Content.jsx:16 only destructures it, and module-assessment/src/pages/AssessmentRunner.jsx:465 requests a `logout` that the context does not provide. `shared-design-system` is also a `file:` dependency of the modules (structural review, Notes) and renders a demonstration page independently; this does not connect units at runtime. Classification counts 10 units and excludes the design system; here it enters as a target, as in the structural and source code reviews.
