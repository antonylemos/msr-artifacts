# 270 — shreyash1086/mfe

## Leitura do repositório

Plataforma de laboratórios e avaliações em React com Webpack 5 Module Federation, Docker e nginx. O `shell-app` é o host: carrega nove remotes `module-*` em runtime, um por rota (shell-app/src/App.jsx:167-277), e os envolve com autenticação e tema próprios (shell-app/src/App.jsx:290-297). O `shared-design-system` é um terceiro papel: remote federado (`name: "sharedDesignSystem"`, shared-design-system/webpack.config.js:36-49) consumido pelo shell e pelos nove módulos, que dele recebem o `ThemeProvider`, o CSS global e componentes como `PageHeader` e `Card`. Os módulos não carregam uns aos outros. O README ainda descreve só três módulos (README.md:4, 9-17), mas o snapshot tem nove, todos ligados ao shell.

As duas cadeias de carga usam a mesma federação de formas diferentes. Para os nove módulos, o shell não declara `remotes` no webpack (comentário em shell-app/webpack.config.js:32-33): um loader próprio injeta o `remoteEntry.js` por `<script>`, inicializa o escopo compartilhado e pede o módulo exposto ao container (shell-app/src/remotes/remoteLoader.js:4-65), com a URL lida de `window.__RUNTIME_REMOTE_CONFIG__` (shell-app/src/config/remoteConfig.js:21-31). Esse objeto é montado no `index.html` do shell: caminhos relativos atrás do gateway quando a porta é 80/443 ou vazia, `localhost:3001`–`3010` no desenvolvimento (shell-app/public/index.html:18-51). No Docker, o gateway (nginx/nginx.conf:18-134) encaminha cada `/<nome>-remote/remoteEntry.js` ao contêiner do serviço do docker-compose.yml. Para o design system, o shell e cada módulo declaram o remote `sharedDesignSystem` como `promise`, que primeiro reusa `window.sharedDesignSystem` e só injeta o script se ele não existir (ex.: module-assessment/webpack.config.js:39-50, :41). Quando um módulo roda dentro do shell, ele reaproveita o container já carregado pelo shell.

Além da carga de módulos, as unidades trocam dois tipos de estado. O `AuthProvider` do shell publica a ponte `window.__SHELL_AUTH__` (shell-app/src/contexts/AuthContext.jsx:228-262), com getters, `onAuthChange` e `signOut`, e avisa os assinantes no login e no logout (shell-app/src/contexts/AuthContext.jsx:45, 137, 219); os nove módulos assinam a ponte quando a encontram e, sem ela, usam o Amplify por conta própria (ex.: module-dashboard/src/AuthContext.jsx:111-145). O tema passa pela chave `theme` do `localStorage` e pela classe `dark` do `documentElement`, gravadas pelo `ThemeProvider` exposto (shared-design-system/src/contexts/ThemeContext.jsx:14-22) em cada instância: a do shell e a de cada módulo. Como a mesma dupla shell–módulo troca os dois estados, e as INSTRUCTIONS juntam numa linha o mesmo trio Origem, Destino e Tipo, cada par tem uma só linha `communication` com as duas evidências e mecanismo `events`, conforme a decisão registrada no fim.

O que não virou relação: os dois `<iframe>` mostram um cliente Guacamole externo com a tela de uma VM, não uma unidade frontend (revisão de código-fonte, module-assessment/src/pages/KodeEnvSection.jsx:369 e module-code-module/src/CodeModule.jsx:847, ambos `No`). O `signOut` dos módulos repassa ao da ponte (ex.: module-dashboard/src/AuthContext.jsx:148-151), mas nenhum módulo o chama: module-content-uploading/src/Content.jsx:16 só o desestrutura, e module-assessment/src/pages/AssessmentRunner.jsx:465 pede um `logout` que o contexto não fornece. O `shared-design-system` também é dependência `file:` dos módulos (revisão estrutural, Notas) e renderiza uma página de demonstração sozinho; isso não liga unidades em runtime. A classificação conta 10 unidades e não o design system; aqui ele entra como destino, como nas revisões estrutural e de código-fonte.
