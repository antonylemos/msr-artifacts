# 254 — marcos-roberto-dev/poc-mfe-custom-root

## Leitura do repositório

Prova de conceito single-spa com Vue 3 em quatro projetos independentes, sem workspace na raiz. `content-app` e `topbar-app` são aplicações Vite que só exportam os lifecycles `bootstrap`, `mount` e `unmount` criados por `singleSpaVue` (content-app/src/main.ts:8-22; topbar-app/src/main.ts:8-22). A montagem própria está comentada nas duas (content-app/src/main.ts:6; topbar-app/src/main.ts:6), então a UI delas só sobe quando um host chama `mount`. Os outros dois projetos são hosts alternativos que compõem os mesmos dois remotos pelas mesmas URLs de servidor de desenvolvimento Vite.

`root-app` é um "custom root" em Vue. Ele não usa `registerApplication`. Seu template raiz tem dois `ParcelWrapper`, um para `@org/header-app` e outro para `@org/content-app` (root-app/src/App.vue:8-9). Cada wrapper carrega o módulo pelo nome com `dynamicImport` (root-app/src/components/ParcelWrapper.vue:21-22), que tenta o `import()` nativo (root-app/src/utils/dynamicImport.ts:15) e, se ele falhar, `System.import` (root-app/src/utils/dynamicImport.ts:22-24). Depois monta o módulo como parcel com o componente `Parcel` de `single-spa-vue/parcel` e `mountRootParcel` (root-app/src/components/ParcelWrapper.vue:3-5, 10-11, 46). Os nomes são resolvidos pelo import map nativo da página (root-app/index.html:11-18). `root-classic` é a root config clássica do `create-single-spa`: webpack, `single-spa-layout` e import map injetado. O layout põe `@org/topbar-app` e `@org/content-app` na rota padrão (root-classic/src/microfrontend-layout.html:20-25). A root config constrói as aplicações a partir desse layout, carrega cada uma por `import(name)`, registra todas com `registerApplication` e chama `start()` (root-classic/src/org-root-config.ts:9-20). O import map com as duas unidades só é emitido em modo local (root-classic/src/index.ejs:29-39), ligado pelo `--env isLocal` do script `start` (root-classic/package.json:4; root-classic/webpack.config.js:21-22). O mapa de produção está comentado (root-classic/src/index.ejs:27).

A ligação entre nomes e unidades é desigual. `@org/content-app` e `@org/topbar-app` repetem o `name` dos `package.json` das unidades (content-app/package.json:2; topbar-app/package.json:2). Já `@org/header-app`, o nome que o `root-app` usa para o topbar, não corresponde a nenhum nome do snapshot. Ele só se liga ao `topbar-app` porque sua URL, `http://127.0.0.1:5175/src/main.ts` (root-app/index.html:15), é a mesma do `@org/topbar-app` no outro host (root-classic/src/index.ejs:35). Nessa URL, o único elemento que distingue a unidade é a porta, porque o caminho `/src/main.ts` existe nos dois remotos. Além disso, nenhuma configuração fixa as portas 5174 e 5175 (content-app/vite.config.ts:5-7; topbar-app/vite.config.ts:5-20). Por isso a relação 4 fica com o nome como aparece no artefato (ver Observações).

O que não virou relação. O mapa SystemJS do `root-app`, que apontaria `@org/header-app` para o build `app.js` do topbar, está comentado (root-app/index.html:24-30). Com isso, o fallback `System.import` fica sem alvo confirmado. Esse caminho é parecido com o build `format: "system"`, com saída `app.js` (topbar-app/vite.config.ts:14-15). `root-app/src/importMap.json`, `root-app/src/importMap.dev.json` e `root-app/mfe-app.json` repetem os nomes com outras URLs (por exemplo, a porta 5173 para o content em root-app/mfe-app.json:4), mas nenhum arquivo do snapshot os lê. A cópia local do topbar em `root-app/src/modules/Topbar/` tem o import e o uso comentados (root-app/src/App.vue:3, 7). `import('@org/root-config')` carrega a própria root config (root-classic/src/index.ejs:33, 53). O `root-app` passa a cada parcel as props fixas `{ text: 'Hello world' }` (root-app/src/components/ParcelWrapper.vue:5, 51-53), e os eventos `parcelMounted`/`parcelUpdated`/`parcelError` só geram log no host (root-app/src/components/ParcelWrapper.vue:3-4, 55-65). Não há troca de mensagens entre unidades: não há `CustomEvent`, `postMessage` nem `BroadcastChannel` no snapshot.

## Observações

**1. root-app → content-app.** O `ParcelWrapper` com `app-name="@org/content-app"` (root-app/src/App.vue:9) carrega o nome por `import()` nativo (root-app/src/components/ParcelWrapper.vue:22; root-app/src/utils/dynamicImport.ts:15). O import map nativo resolve esse nome para `http://127.0.0.1:5174/src/main.ts` (root-app/index.html:14). O destino foi identificado pelo nome, que repete o `name` do `package.json` da unidade (content-app/package.json:2), e não pela porta. O wrapper usa o próprio namespace do módulo como configuração da parcel, desde que tenha `mount` e `unmount` (root-app/src/components/ParcelWrapper.vue:27, 33), e o monta com `mountRootParcel` (root-app/src/components/ParcelWrapper.vue:46). Esses lifecycles são os exportados em content-app/src/main.ts:20-22. O tipo é `host → remote` porque o destino entra como módulo carregado em runtime e montado como parcel, sem registro no orquestrador (`registerApplication`). O mecanismo é `single-spa`, pelos lifecycles e pelo `mountRootParcel`. Ativa `Yes` pelas linhas `Yes` da revisão de código-fonte. A linha `Undetermined` do fallback `System.import` (root-app/src/utils/dynamicImport.ts:24) faz parte do mesmo caminho de carga e não muda o valor. A porta 5174 depende da ordem de subida dos servidores, porque não está fixada em content-app/vite.config.ts:5-7.

**2. root-classic → content-app.** O layout põe `<application name="@org/content-app">` na rota `default` (root-classic/src/microfrontend-layout.html:21-23). A root config transforma o layout em rotas e aplicações e carrega cada uma por `import(name)` (root-classic/src/org-root-config.ts:9-15). Em seguida registra as aplicações com `registerApplication` e chama `start()` (root-classic/src/org-root-config.ts:18, 20). O nome é resolvido pelo import map local para a mesma URL da relação 1 (root-classic/src/index.ejs:34) e corresponde ao `name` da unidade (content-app/package.json:2). O tipo é `root-config → application` porque o destino entra registrado no orquestrador, embora a carga seja um `import()`. Ativa `Yes` pelas linhas `Yes`, com a ressalva de que o mapa só existe com `isLocal` (root-classic/src/index.ejs:29-39). As linhas dos lifecycles do content-app sustentam as relações 1 e 2 e aparecem nas duas.

**3. root-classic → topbar-app.** Mesmo caminho da relação 2, com `<application name="@org/topbar-app">` (root-classic/src/microfrontend-layout.html:22). O nome é resolvido para `http://127.0.0.1:5175/src/main.ts` (root-classic/src/index.ejs:35) e corresponde ao `name` do `package.json` do topbar (topbar-app/package.json:2). Os lifecycles consumidos são os de topbar-app/src/main.ts:20-22. As duas aplicações estão na mesma rota e são montadas juntas dentro do `<main>`. A ordem é a do layout: o topbar primeiro (root-classic/src/microfrontend-layout.html:20-24). Ativa `Yes`, com a mesma ressalva de modo local da relação 2.

**4. root-app → @org/header-app.** O segundo `ParcelWrapper` do `root-app` carrega `@org/header-app` (root-app/src/App.vue:8) pelo mesmo caminho da relação 1. O import map resolve esse nome para `http://127.0.0.1:5175/src/main.ts` (root-app/index.html:15). Nenhuma unidade do snapshot se chama `header-app`. A correspondência com o `topbar-app` só aparece quando se compara essa URL com a do `@org/topbar-app` no outro host (root-classic/src/index.ejs:35). Nessa URL, só a porta 5175 distingue a unidade, porque o caminho `/src/main.ts` é comum aos dois remotos e a porta não está fixada em topbar-app/vite.config.ts:5-20. Como porta sozinha não basta, o destino fica com o nome como aparece no artefato, e No snapshot fica `Undetermined`. A cópia comentada do topbar em `root-app/src/modules/Topbar/` (root-app/src/App.vue:3, 7) e o `<header>` do App do topbar (topbar-app/src/App.vue:2) sugerem o mesmo alvo, mas não são correspondência explícita. Se a URL igual nos dois hosts fosse aceita como correspondência, o destino seria `topbar-app`, com No snapshot `Yes`, e as linhas topbar-app/src/main.ts:4, 8 e 20-22 também entrariam nesta relação. Isso não muda as contagens do Resumo, porque o topbar-app já está na relação 3. Ativa `Yes` pelas linhas `Yes` de root-app/src/App.vue:8, root-app/src/components/ParcelWrapper.vue:3 e root-app/src/utils/dynamicImport.ts:15. A revisão de código-fonte já atribui essas linhas ao topbar-app pela coincidência de URL, com o critério dela. Esta relação só aplica a regra do Destino desta etapa e não a corrige.
