# 356 — nurazizUGM-Intero5/OpenMRS-Module-Patient

## Repository overview

A copy of monorepo `openmrs-esm-patient-chart`, the OpenMRS 3 frontend module bringing together "various microfrontends that constitute widgets in a patient dashboard" (README.md:7). Its 18 `packages/esm-*-app` units are ESM modules: each declares its offered extensions (component + slot), workspaces and modals in `src/routes.json`. The OpenMRS app shell, loading modules through the import map and mounting those declarations, is absent from the snapshot: development uses external tooling `openmrs` (package.json:9, `openmrs develop`) and import map overrides (README.md:56). Hence no snapshot unit hosts all others; each unit hosts others wherever it mounts a slot or opens a workspace or modal by name. Its purpose is a product, inherited from upstream, with a single owner commit having no effect on composition.

Almost all relationships (45 of 58) are `host → remote`, 43 with mechanism `other`: the source mounts an `ExtensionSlot` or calls `launchWorkspace`/`launchPatientWorkspace`, `useLaunchWorkspaceRequiringVisit`, `showModal` or `closeWorkspace` with a name, and framework `@openmrs/esm-framework` loads the component registered by the target with that name in its `routes.json`. Target was resolved through that slot, workspace or modal name. Type is `host → remote` because the target enters the source as an exposed component loaded at runtime; mechanism is `other` because this is the framework's extension system, rather than Module Federation or `registerApplication` performed by the source. Exceptions are relationships 1 and 2, targeting `packages/esm-form-entry-app`: that Angular app's component `formWidget` imports `./bootstrap` (packages/esm-form-entry-app/src/index.ts:66), generating and exporting `singleSpaAngular` lifecycles (packages/esm-form-entry-app/src/bootstrap.ts:12-23), hence recorded mechanism `single-spa`. This is the only snapshot location where the single-spa foundation and Module Federation container loaded by shell (packages/esm-form-entry-app/webpack.config.js:70-76) are visible. In the 17 React apps, `webpack.config.js` only delegates to external package `openmrs/default-webpack-config`.

Composition centers on `packages/esm-patient-chart-app`, the patient chart page. It mounts the banner, flags bar, side navigation and dashboards from slots filled by other units and opens their workspaces. Order units (`orders`, `medications`, `tests`) open one another through cart `order-basket`. The form engine (`form-engine` and `form-entry`) enters through `form-widget-slot` in `forms` and `vitals`. Many calls pass through helpers in library `packages/esm-patient-common-lib`, not counted as a unit by the structural review. In those cases, Source is the unit calling the helper. Thus `useLaunchWorkspaceRequiringVisit` opens chart modal `visit-context-switcher` or `start-visit-dialog` when there is no visit (packages/esm-patient-common-lib/src/workspaces.ts:52-63), connecting each unit using the hook to chart.

There is also state and message exchange. Both library global stores, `order-basket` and `patient-chart-global-store`, are created through `createGlobalStore` and shared by name in the framework, a reactive service; they became `communication` with mechanism `events` (relationships 36-43). The flags module listens to shell's `single-spa:routing-event` (relationship 6). `forms` embeds the OpenMRS 2.x HFE-UI page in an iframe and receives its `postMessage` (relationships 3 and 45). `form-engine` exchanges two `window` events whose other endpoint is absent from the snapshot (relationships 4 and 5).

Thirteen relationships have only named targets: slots filled by no snapshot `routes.json` (for example `top-of-all-patient-dashboards-slot`, `visit-form-top-slot`, `medication-info-slot`), dynamically named slots and workspace `appointments-form-workspace`. They may be filled by modules in other repositories or remain empty, hence Target uses the name, with In snapshot and Active `Undetermined`. What did not become a relationship: slots, workspaces and modals mounted by the unit from itself (internal, as already recorded by the source code review); the no-visit branch of `launchFormEntryOrHtmlForms` when chart itself calls it, opening chart's `start-visit-dialog` (packages/esm-patient-common-lib/src/form-entry-interop.ts:51-53); with a visit, the same call (packages/esm-patient-chart-app/src/visit/visits-widget/past-visits-components/encounters-table/encounters-table.component.tsx:242, :287) opens forms' form workspaces (packages/esm-patient-common-lib/src/form-entry-interop.ts:28-50) and enters relationship 10; extensions registered in slots mounted by no snapshot unit (for example `action-menu-patient-chart-items-slot`, packages/esm-patient-lists-app/src/routes.json:10, mounted by the external shell). Hence `packages/esm-patient-lists-app` has no relationship.
