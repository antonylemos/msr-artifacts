# 025 — raiane-honorato/software-eng-mba

## Repository overview

An MBA final-project repository implementing the same gym app (MyGym) three times to compare modularization approaches in React Native: monolith, Turborepo (build-time) and Re.Pack (runtime) (README.md:27-33). The rule applying to all three versions is that the `check-in` and `dashboard` modules never import each other and communicate only through the shared Zustand store `@mygym/store` (README.md:16-23). Only the Re.Pack version composes units at runtime. The monolith (`apps/monolith`) and Turborepo app (`apps/turborepo/apps/mygym`) are isolated units; Turborepo joins features as workspace packages in a single bundle, and those packages are not units in the structural review.

In the Re.Pack version (`apps/repack/packages/`), `host` is the Module Federation 2 host (`Repack.plugins.ModuleFederationPluginV2`) and declares the `checkin` and `dashboard` remotes through platform-specific `mf-manifest.json`, on ports 9001 and 9002 (apps/repack/packages/host/rspack.config.mjs:45-52). Each mini-app exposes a navigation stack without `NavigationContainer`, which resides only in the host (apps/repack/packages/check-in/rspack.config.mjs:45-46; apps/repack/packages/dashboard/rspack.config.mjs:43-44). The host loads each stack with `React.lazy`, maps the named export to `default` and wraps it in `ErrorBoundary` + `Suspense` (apps/repack/packages/host/src/screens/CheckInTab.tsx:11-24). The two `Tab.Navigator` tabs are the entry points: `Home` → dashboard and `FindGyms` → check-in (apps/repack/packages/host/src/navigation/RootNavigator.tsx:52-53). The `shared` list comes from a common helper: the host provides the singletons eagerly and the mini-apps consume the host's instance (apps/repack/packages/shared-deps/sharedDeps.mjs:61-80; apps/repack/packages/host/rspack.config.mjs:53-54). This is how the Zustand store becomes a communication channel between the two mini-apps at runtime.

`apps/repack-poc/` is an earlier spike with a minimal host and remote: the host renders the `HelloScreen` exposed by the remote (apps/repack-poc/README.md:5, 19-20). The README gives the `ErrorBoundary` fallback when the remote goes down as a success criterion, to prove runtime loading. The units are React Native apps, rather than web apps; the mobile × web scope decision remains open in the classification and does not change the relationships recorded here. The remote URLs point to `localhost`, and the MF manifests are generated by the dev server, with no versioned copy in the snapshot.

Port 9001 is not in the remote's `start` (apps/repack-poc/remote/package.json:9); it comes from the documented `pnpm react-native start --port 9001` command (apps/repack-poc/README.md:100-101) and only corroborates. The remote has `export default` (apps/repack-poc/remote/src/HelloScreen.tsx:11), which is what `React.lazy` resolves.

**2. apps/repack/packages/host → apps/repack/packages/check-in.** The `checkin` remote (apps/repack/packages/host/rspack.config.mjs:50) matches the check-in unit through `name: 'checkin'` and the `exposes` of `./CheckInStack` (apps/repack/packages/check-in/rspack.config.mjs:42-46). The `start` port 9001 (apps/repack/packages/check-in/package.json:9) matches the remote URL, as recorded in apps/repack/mprocs.yaml:2-3. The host obtains the named `CheckInStack` export (apps/repack/packages/host/src/screens/CheckInTab.tsx:12), which the mini-app defines in apps/repack/packages/check-in/src/navigation/CheckInStack.tsx:8. The source code review's `RootNavigator.tsx:52` line covers both tabs and therefore appears in this relationship and in 3.

**4. apps/repack/packages/check-in ↔ apps/repack/packages/dashboard (communication).** The channel is `useCheckInStore` (apps/repack/packages/store/src/checkInStore.ts:33), in a package that is not a unit. It becomes a single state across the mini-apps by being a Module Federation singleton provided by the host. The host only provides the store and neither reads nor writes it, so it is not part of the relationship. The README describes check-in as producer and dashboard as consumer (README.md:20-21), but the code sends in both directions. Check-in writes by calling `startCheckIn` (apps/repack/packages/check-in/src/screens/CheckInConfirmationScreen.tsx:52), and dashboard reads `isActive` to choose the screen (apps/repack/packages/dashboard/src/navigation/DashboardStack.tsx:12-17). Dashboard writes by calling `endCheckIn` and `saveRating` (apps/repack/packages/dashboard/src/screens/WorkoutFinishScreen.tsx:50-53), which write `history` (apps/repack/packages/store/src/checkInStore.ts:69-76). Check-in reads that history through `canCheckInToday` (apps/repack/packages/store/src/checkInStore.ts:85-90), which enables check-in in the gym list and confirmation (apps/repack/packages/check-in/src/screens/GymListScreen.tsx:17; apps/repack/packages/check-in/src/screens/CheckInConfirmationScreen.tsx:35). Therefore direction is `bidirectional`. The mechanism is `events`, as a shared reactive service. The relationship is active because the source code review line is `Yes`.
