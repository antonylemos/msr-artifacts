# 109 — ramdev90/nx-module-federation

## Repository overview

An Angular example in an Nx workspace, largely generated by the tool's scaffold (NxWelcome screens, example configuration comments). `shell` is the host and `customer`, `orders` and `products` are Module Federation remotes. The shell declares all three by name (shell/module-federation.config.ts:17), and each remote exposes key `./Routes`, pointing to its `entry.routes.ts` (customer/module-federation.config.ts:4-7; orders/module-federation.config.ts:4-7; products/module-federation.config.ts:4-7). All four configurations are passed to `withModuleFederation` from `@nx/module-federation/angular` (shell/webpack.config.ts:1-2, 9, with an identical file in the other three units), and builds read them through `customWebpackConfig` (shell/project.json:24-25). There is no remote URL: Nx resolves each name to a project in the same workspace, and the shell starts remotes with executor `@nx/angular:module-federation-dev-server` (shell/project.json:60).

Composition is through routes. The shell loads `customer/Routes`, `orders/Routes` and `products/Routes` in `loadChildren` and uses each one's `remoteRoutes` (shell/src/app/app.routes.ts:4-16); routes are registered by `provideRouter(appRoutes)` (shell/src/app/app.config.ts:9) and presented through a menu with `router-outlet` (shell/src/app/app.html:1-7). The contract is only an Angular route list; the `customer` and `orders` entries show NxWelcome (customer/src/app/remote-entry/entry.ts:5-7; orders/src/app/remote-entry/entry.ts:5-7), and `products` adds the `list` route with component `ProductList` (products/src/app/remote-entry/entry.routes.ts:5-8). The `customer/Routes` etc. aliases in tsconfig.base.json:17-20 provide typing for those same federated specifiers.

The distinctive feature is lateral coupling between two remotes outside federation: the `orders` NxWelcome imports `ProductList` from `products` sources through a relative path (orders/src/app/remote-entry/nx-welcome.ts:3, 7) and renders `<app-product-list>` (orders/src/app/remote-entry/nx-welcome.ts:512), outside the template's commented-out block. This became relationship 4, type `other`. The initial `apps/microfrontend-workspace` application is an isolated unit: empty routes (apps/microfrontend-workspace/src/app/app.routes.ts:1-3) and no connection to the other four. There is no explicit inter-unit communication (source code review, Notes). The external remote in shell/module-federation.config.ts:9 is a commented-out scaffold example and did not enter as a relationship.

**1. shell → customer.** The shell's `customer` remote (shell/module-federation.config.ts:17) matches the customer unit through `name: 'customer'` and key `./Routes` (customer/module-federation.config.ts:4-7), the specifier imported in shell/src/app/app.routes.ts:7; the exposed file exports `remoteRoutes` (customer/src/app/remote-entry/entry.routes.ts:4), which the shell reads. No URL or `publicPath` is declared; port 4203 (customer/project.json:62) only corroborates. Active because both code lines are `Yes` and `appRoutes` is registered by shell/src/app/app.config.ts:9. The shell/src/app/app.routes.ts:4 line (`appRoutes`) also supports relationships 2 and 3.

**2. shell → orders.** The same resolution: remote `orders` (shell/module-federation.config.ts:17), `name: 'orders'` and `./Routes` (orders/module-federation.config.ts:4-7), import in shell/src/app/app.routes.ts:11 and `remoteRoutes` in orders/src/app/remote-entry/entry.routes.ts:4. The exposed route shows orders' NxWelcome (orders/src/app/remote-entry/entry.ts:5-7), where relationship 4 resides.

**3. shell → products.** The same resolution: remote `products` (shell/module-federation.config.ts:17), `name: 'products'` and `./Routes` (products/module-federation.config.ts:4-7), import in shell/src/app/app.routes.ts:15 and `remoteRoutes` in products/src/app/remote-entry/entry.routes.ts:5-8. It is the only remote with more than one route (`''` and `list`). The shell menu points only to each remote's root (shell/src/app/app.html:3-5).

**4. orders → products.** `orders` embeds the `ProductList` component from `products` by importing the source file through a relative path leaving the project (orders/src/app/remote-entry/nx-welcome.ts:3), declaring it in `imports` (orders/src/app/remote-entry/nx-welcome.ts:7) and using tag `<app-product-list>` (orders/src/app/remote-entry/nx-welcome.ts:512; selector in products/src/app/product-list.ts:4). The target is the products unit through the file path. This is neither Module Federation nor a custom element: the component enters orders' bundle at build time, hence type and mechanism `other`, as in the source code review. No configuration declares this connection. Active because the line is `Yes`: NxWelcome is the component on orders' exposed route (orders/src/app/remote-entry/entry.ts:2-7; orders/src/app/remote-entry/entry.routes.ts:4), so it appears both in standalone orders and inside the shell. `ProductList` only shows "Product List works!" (products/src/app/product-list.html:1-3).
