# 084 — pmiguras/likekiri-website

## Repository overview

A production-oriented modular platform with two React/Vite hosts and ten federated modules in the same pnpm monorepo. `apps/admin-shell` is the administration panel SPA and `apps/web-shell` is the public site shell, rendered on the server and completed by client islands. The ten `modules/*` are `@module-federation/vite` remotes generating only a `remoteEntry.js` (for example, modules/hello/vite.config.ts:10-16), each running its own `server.mjs` to serve the bundle and publish a signed manifest at `/.well-known/module-manifest` (modules/hello/server.mjs:122-123). For each exposed component, the manifest states which surface (`web` or `admin`) and route it enters (modules/hello/server.mjs:34-53). Between hosts and modules is `apps/core`, a NestJS backend that is not a frontend unit: it fetches the registered modules' manifests (apps/core/src/registry/registry.service.ts:401-406), compiles a per-surface route table with `moduleId` and `remoteEntry` (apps/core/src/registry/registry.service.ts:466-486) and delivers it to the shells.

Both hosts enter modules through the Module Federation runtime, without static `remotes`. The panel requests the `admin` surface manifest from core (apps/admin-shell/src/api.ts:85), matches the current route (apps/admin-shell/src/App.tsx:214), and `ModulePage` calls the loader, which registers the remote with `init`/`registerRemotes` and obtains `${moduleId}/${exposed}` through `loadRemote` (apps/admin-shell/src/federation.ts:34-46); the component is mounted in apps/admin-shell/src/views/ModulePage.tsx:48. On the site, core matches the public route, executes web-shell's SSR render within its own process (apps/core/src/shell/shell.service.ts:89, :147) and passes the module island descriptor and global widgets; the shell writes `data-likekiri-island`/`data-remote` placeholders into HTML (apps/web-shell/src/entry-server.tsx:57-58, :79-80), and the island runtime reads those attributes, initializes remotes and loads and mounts each component (apps/web-shell/src/islands.ts:22-44, :54-67, :90-107). The `clientes` module adds delegated SSR: core requests HTML from the module server's `/render` (apps/core/src/registry/registry.service.ts:307-318), the shell inserts it in the placeholder (apps/web-shell/src/entry-server.tsx:96) and the client hydrates it (apps/web-shell/src/islands.ts:65).

No shell line names a module: targets arrive through runtime data. This review resolved them through each module's declarations about itself in the snapshot: federation `name` equals manifest `MODULE_ID`, route `component` values are the `exposes`, and `surface` indicates which shell receives the component (core filters the table by surface in apps/core/src/registry/registry.service.ts:213-223). Thus the panel consumes nine modules (all except `ejemplo-web`) and the site consumes four (`chat`, `clientes`, `ejemplo-web` and `hello`). The limitation is the list of modules enabled in a deployment: it resides in `config/modules.json`, outside the snapshot; the only versioned example registers only `hello` (config/modules.example.json:4-5). All ten modules nevertheless have their own process and proxy in the versioned infrastructure (structural review, Deploy column). There are no custom elements, iframes or inter-unit message exchanges; the props passed to islands and pages (apps/web-shell/src/islands.ts:62, apps/admin-shell/src/views/ModulePage.tsx:48) are loading data, rather than a communication channel. The `packages/*` libraries are shared during build and are not composed units.

## Observations

**1. apps/admin-shell → modules/chat.** The panel receives only `admin` surface routes from core (apps/admin-shell/src/api.ts:85; surface filter in apps/core/src/registry/registry.service.ts:213-223), and the loader requests `${route.moduleId}/${exposed}` (apps/admin-shell/src/federation.ts:44-45). The target was resolved through `MODULE_ID = 'chat'` (modules/chat/server.mjs:43), equaling federation `name` (modules/chat/vite.config.ts:9), and the `admin` routes with `./ChatAdminPage`, one of the `exposes` (modules/chat/server.mjs:496-497; modules/chat/vite.config.ts:13). The core lines (apps/core/src/registry/registry.service.ts:403) have Unit `—` in the source code review, but belong here because the manifest obtained there is the source of the `moduleId` and `remoteEntry` used by the panel. All constructs are `Yes`, so the relationship is active. Whether the module is enabled in a deployment depends on `config/modules.json`, outside the snapshot (see Overview); this does not change target identity. This pair also has relationship 10 with the site, through the other exposure.

**2. apps/admin-shell → modules/clientes.** The same path as relationship 1. The target is `clientes` through `MODULE_ID` (modules/clientes/server.mjs:45) and federation `name` (modules/clientes/vite.config.ts:23); the `admin` routes use `./CuentasAdminPage` and `./FacturacionAdminPage` (modules/clientes/server.mjs:1016-1017), exposed in modules/clientes/vite.config.ts:29-30. The module's delegated SSR applies only to `web` routes and belongs to relationship 11.

**11. apps/web-shell → modules/clientes.** The site loads the three `clientes` islands through the same runtime (apps/web-shell/src/islands.ts:54, :90), resolved through `MODULE_ID = 'clientes'` (modules/clientes/server.mjs:45) and the `web` routes (modules/clientes/server.mjs:1013-1015), whose components are exposed in modules/clientes/vite.config.ts:26-28. This is a mixed relationship; type follows how the component enters the host, loaded as a module, and delegated SSR remains in the same record. All constructs are `Yes`.

**12. apps/web-shell → modules/ejemplo-web.** The same page path as relationship 11, without delegated SSR. `MODULE_ID = 'ejemplo-web'` (modules/ejemplo-web/server.mjs:24) and `name: 'ejemplo-web'` (modules/ejemplo-web/vite.config.ts:12); the `web` route `/ejemplo-web/:modo` uses `./SimuladorIsland` with `ssr: 'shell'` (modules/ejemplo-web/server.mjs:42-48), so the shell writes only the placeholder (apps/web-shell/src/entry-server.tsx:79) and the island is mounted on the client (apps/web-shell/src/islands.ts:67). **13. apps/web-shell → modules/hello.** The same path as relationship 12. `MODULE_ID = 'hello'` (modules/hello/server.mjs:23) and `name: 'hello'` (modules/hello/vite.config.ts:11); the `web` route `/hello/:slug` uses `./HelloIsland` with `ssr: 'shell'` (modules/hello/server.mjs:41-47; modules/hello/vite.config.ts:14). Together with relationship 5, `hello` is one of the three modules entering both surfaces, alongside `chat` and `clientes`.
